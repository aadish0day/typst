# Extreme Programming (XP)
Extreme Programming (XP) is an Agile software development methodology that focuses on:
* High software quality
* Customer satisfaction
* Continuous feedback
* Team collaboration
* Frequent software releases
* Adaptability to changing requirements

XP was developed by Kent Beck in the late 1990s while working on the Chrysler Comprehensive Compensation System (C3) project.

![https://upload.wikimedia.org/wikipedia/commons/thumb/5/55/Kent_Beck_no_Workshop_Mapping_XP.jpg/250px-Kent_Beck_no_Workshop_Mapping_XP.jpg](Picture2.jpg)
Why is it called “Extreme”?
XP takes good software engineering practices to an extreme level.

# Need for XP:
XP addresses these issues by encouraging:
* Rapid feedback
* Frequent releases
* Continuous improvement
* Strong teamwork
* Simple designs
Traditional software development suffered from:
* Long development cycles
* Poor communication
* Late customer feedback
* High defect rates
* Difficulty handling changing requirements

# Core Values of Extreme Programming
Kent Beck originally proposed 4 values, later expanded to 5 values.

Value 1: Communication
Value 2: Simplicity
Value 3: Feedback
Value 4: Courage
Value 5: Respect

![What Is Extreme Programming (XP)? - Values, Principles, And Practices](Picture2.jpg)

### Notes:

<!-- Slide number: 6 -->
# Value 1: Communication
Software development is a team activity.
Developers, testers, customers, and managers should communicate continuously.
Poor communication causes:

* Wrong requirements
* Delays
* Bugs
* Rework
XP promotes communication through:

* Pair Programming
* Daily discussions
* Customer collaboration
* Team planning meetings
Example: Instead of emailing for clarification after three days, the customer is available to answer immediately.

### Notes:

<!-- Slide number: 7 -->
# Value 2: Simplicity
Principle: Build only what is needed today.
Avoid unnecessary features.

Rule
“Do the simplest thing that could possibly work.”
Benefits

* Easier maintenance
* Fewer bugs
* Faster development
* Lower cost
Example:Instead of designing for 100 future features, implement only the current requirement.

### Notes:

<!-- Slide number: 8 -->
# Value 3: Feedback
XP believes feedback should be received as early as possible.

Feedback comes from:
* Customers
* Unit tests
* Integration tests
* Team members
Benefits

* Early error detection
* Improved software quality
* Better customer satisfaction

### Notes:

<!-- Slide number: 9 -->
# Value 4: Courage
Developers should have courage to:
* Refactor code
* Remove unnecessary code
* Accept feedback
* Change designs
* Admit mistakes
Example: Deleting 500 lines of unnecessary code even after spending hours writing it.

### Notes:

<!-- Slide number: 10 -->
# Value 5: Respect
Added in later editions of XP.
Every team member should respect others.

Respect includes:
* Listening to teammates
* Valuing customer opinions
* Writing quality code
* Helping teammates

# Core Practices of XP
Practice 2: Small Releases

Deliver software frequently.
Release every:
1 week
2 weeks
3 weeks

Outcome:
Quick feedback
Early bug detection

Practice 1: Planning Game

Developers and customers jointly plan.

Outcome:
Iteration plan.

Practice 3: System Metaphor

A simple shared vision or analogy describing how the system works.

Outcome :
Everyone understands the architecture.

### Notes:

<!-- Slide number: 13 -->
# Core Practices of XP
Practice 5: Testing (Test-Driven Development)

TDD Cycle
Write a failing test.
Write minimal code to pass the test.
Refactor the code.
Repeat.

Practice 4: Simple Design

Design only what is necessary.

Good design should:
Pass tests
Avoid duplication
Be easy to understand
Contain minimal code

Practice 6: Refactoring

Improve code without changing functionality.

Examples:
Rename variables
Remove duplicate code
Simplify methods
Improve structure

Outcome:
Cleaner code
Better readability
Easier maintenance

### Notes:

<!-- Slide number: 14 -->
# Core Practices of XP

Practice 8: Collective Code Ownership

Anyone can modify any part of the code.

Outcome:
No dependency on one programmer
Faster bug fixing
Better collaboration

Practice 9: Continuous Integration (CI)

Developers integrate code many times each day.

Each integration triggers:
Build
Unit tests
Integration tests

Benefits:
Early detection of conflicts
Stable codebase
Faster development

Practice 7: Pair Programming

Two developers work on one computer.

### Notes:

<!-- Slide number: 15 -->
# Core Practices of XP

Practice 11: On-Site Customer

Customer works closely with the team.

Responsibilities:
Clarify requirements
Prioritize features
Answer questions
Accept completed work

Benefits:
Fewer misunderstandings
Faster decisions
Better product fit

Practice 12: Coding Standards

Entire team follows common coding rules.

Examples:
Naming conventions
Formatting
Documentation
File organization

Benefits:
Easier maintenance
Consistent code
Better readability

Practice 10: Sustainable Pace (40-Hour Week)

Developers should avoid chronic overtime.
