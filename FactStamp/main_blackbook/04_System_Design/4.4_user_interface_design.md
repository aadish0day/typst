## UI Architecture

FactStamp's frontend is a fully custom component system — there is no third-party UI kit (no Material UI, no Chakra, no shadcn/ui component import). Every interactive primitive (`Button`, `Input`, `Modal`, `Badge`, `CategoryBadge`, `VerdictPill`, `Avatar`, `SourceQualityDot`, `EmptyState`, `ErrorState`, `Skeletons`, `ThemeToggle`, `LoadingButton`, `PasswordStrength`, `ShimmerText`, `Marquee`, `FlowButton`, `InteractiveHoverButton`, `SpotlightCard`) lives in `src/components/ui/` and is styled with **Tailwind CSS v4**, using CSS custom properties (`--color-brand`, `--color-v-true`, `--color-surface`, etc.) rather than hard-coded utility colors, so the entire application can flip between light and dark themes by swapping the custom-property values at the root rather than duplicating class lists. **Framer Motion** drives the app's signature "tactile stamp" motion language (verdict badges mounting with a physical stamp-impact scale/rotation animation) and shared transitions across the Navbar, Footer, and Admin console theme toggle. **Recharts** renders every chart in the Dashboard and Admin Overview tab, with custom tooltip components replacing Recharts' default chrome. State is managed exclusively through **React Context** (`AuthContext`, `ClaimsContext`, `NotificationsContext`, `ThemeContext`, `UsersContext`) — no Redux or other external state library, a deliberate choice given the app's shallow, loosely-coupled state graph (Chapter 2, Section 2.2).

## Screen-by-Screen Wireframe Descriptions

### Home (`/`)

The landing page opens with a hero section explaining FactStamp's purpose (community-powered WhatsApp fact-checking) and a primary call-to-action to submit a claim or browse the verification queue. Below the hero, the page surfaces live platform statistics (claims resolved, active verifiers, category coverage) using `AnimatedCounter`, followed by a short "how it works" walkthrough (submit → duplicate check → community quorum → shareable card) and a closing call-to-action. The Navbar (persistent across all public routes) exposes a single "Sign in" button when logged out — registration is reached from the sign-in page rather than from a separate Navbar action. When logged in, the right-hand cluster is `ThemeToggle`, `NotificationBell`, a desktop-only "Submit claim" button (`InteractiveHoverButton`), the user's avatar with name and star-reputation chip, and a logout icon button.

### Submit (`/submit`, protected)

A single-column form: a toggle between two input modes, labelled "Text Forward" and "Screenshot (OCR)". In text mode, a plain textarea captures the claim. In screenshot mode, a drag-and-drop/file-picker zone accepts an image, which triggers client-side compression and Tesseract.js OCR inline, showing a loading state (`Skeletons`) while extraction runs, then populating an editable textarea with the cleaned OCR output so the user can correct any misread text before submission. Below the text field sits the category selector, built from `CategoryBadge` and laid out as a card grid rather than a dropdown. Its five options are labelled "Health & Medical", "Political & Govt", "Financial & Loans", "Religious & Culture" and "Other Topics", each with a short sub-description beneath the label. The Jaccard duplicate check (Module 3) runs when the claim textarea loses focus; if it finds a match, an inline duplicate warning appears with a button linking to the existing claim's `ClaimDetail` page, and the Submit button is disabled so no new claim can be created.

### VerifyQueue (`/verify`, protected)

A scrollable list of `ClaimCard` components, each showing the claim's text excerpt, category badge, submission timestamp, and current verification progress rendered as a three-segment `ConsensusStepper` component. Cards additionally carry a countdown chip derived from `consensusDeadline` ("2d 4h left", or "Consensus closed" once elapsed), an "Expedited Review" badge on admin-flagged claims, a "1 Verdict to Resolve" badge when `verificationCount` is exactly 2, and a "Screenshot Attached" badge where an image was submitted. Admin-flagged claims (`adminFlagged`) are visually distinguished and sorted to the top. A category filter and search bar sit above the list. Clicking any card navigates to `VerifyDetail` for that claim.

### VerifyDetail (`/verify/:claimId`, protected)

The verifier's workbench: the full claim text (and screenshot, if one was attached) is shown at the top, followed by a bare progress line reading "N of 3 verifications recorded". This route deliberately does **not** show the peer verdicts themselves — `VerifyDetail.tsx` renders only the count, while the full list of verifications with their verdicts, sources and explanations appears on the public `ClaimDetail` route. This is **blind review**: a verifier casting a verdict cannot see how others have already voted, which prevents the anchoring and bandwagon effects that would otherwise undermine the independence the 3-verifier quorum depends on. Below the progress line sits the current user's own verification form: a verdict selector (`VerdictPill` options — True, False, Misleading, Unverifiable; `Contested` is never a selectable option here, since it is system-assigned only, per Section 4.1/Section 4.3.1), a source URL input, a `SourceQualityDot` indicator reflecting the domain-whitelist classification of the entered URL, and an explanation textarea with a live character/word counter validated against `validateVerdictExplanation()`'s rules (see Section 4.5) before the Submit button becomes enabled.

### ClaimDetail (`/claim/:claimId`, public)

Publicly viewable regardless of login state. Displays the claim text/screenshot, the final verdict as a large color-coded `VerdictPill` (or a "still under review" state with a progress indicator if `status` is still `pending`), the confidence score as a percentage with a breakdown of its three components (agreement, reputation, source quality), and the list of contributing verifications with their cited sources. A prominent "Download WhatsApp Card (PNG)" button triggers `FactCheckCard.tsx`'s `html-to-image` rasterization and downloads the resulting PNG, exported 1080px wide (a 540px-wide card captured at 2× pixel ratio) with a content-dependent height that adapts to how long the claim text is and how many sources were cited.

### Dashboard (`/dashboard`, public)

A grid of Recharts visualizations: a category-distribution bar chart (Health/Political/Religious/Financial/Other), a verdict-distribution pie chart, a rolling 7-day trending-misinformation list (from `weeklyReport.ts`), and a top-verifiers leaderboard ranked by reputation. Every chart uses custom tooltip components rather than Recharts' default styling, consistent with the design system.

### Profile (`/profile`, protected)

Shows the current user's own account details (display name, email, join date), their reputation score with a visual tier indicator (Novice/Trusted/Expert/Elite — the same tiering used in the Admin Overview chart, the Admin subsection below), a history list of claims they've submitted and verifications they've cast, and account settings (display name edit, theme preference, sign-out).

### Admin (`/admin`, admin-guarded) — 5 Tabs

`Admin.tsx` is a single-page console reached only by typing the unlisted `/admin` URL directly (it is deliberately absent from the public `Navbar`/`Footer`). Before any tab renders, `AdminRoute.tsx` shows a username/password login gate (see Section 4.5). Once authenticated, the console exposes exactly 5 tabs:

- **System Overview** — KPI cards (registered verifiers, total claims, verifications logged, incident queue size) alongside two Recharts visualizations — a claims-by-category bar chart and a verdict-consensus pie chart — plus a verifier reputation-tier breakdown (Novice/Trusted/Expert/Elite) rendered as a plain counts grid of coloured dots rather than as a chart.
- **Verifier Directory** — a searchable/filterable table of every `User` record, with per-row actions to edit a verifier's reputation score, toggle their `isAdmin` flag (promote/revoke), or delete the account.
- **Claims Moderation** — a searchable/filterable table of every `Claim`, with per-row actions to toggle the expedited-review flag (`adminFlagged`), override the verdict/confidence/status, edit the claim's text or category, inspect or delete individual embedded verifications, or hard-delete the claim entirely.
- **Incident Queue** — the `ModerationReport` ticket queue, filterable by `status` (pending/investigating/resolved/dismissed) and `severity` (low/medium/high), with actions to create, resolve, or dismiss a report.
- **Audit & Tools** — an immutable, real-time `AdminAuditLog` viewer, plus system-wide tools: force-run the consensus-expiry sweep on overdue claims, broadcast a notification to all users, and export a full JSON database backup (claims + users + reports + audit logs).

Every mutating action in any tab funnels through a shared `addAuditLog()` helper, so the Audit & Tools tab is a complete record of every administrative action taken anywhere in the console.
