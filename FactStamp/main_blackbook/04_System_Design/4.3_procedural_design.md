## 4.3.1 Logic Diagrams

The primary control-flow logic in FactStamp is the claim lifecycle: **submission → duplicate check → verification queue → consensus**. A logic/flow diagram of this pipeline would show:

1. **Start node:** User submits a claim via `Submit.tsx`, as either typed text or an uploaded screenshot.
2. **Decision — Input type:** If a screenshot was uploaded, branch through `imageCompression.ts` (compress) → `ocrService.ts` (Tesseract.js WASM extraction) → `cleanExtractedOcrText()` (strip WhatsApp chrome) → user review/edit of the extracted text. If raw text was pasted, skip directly to the next step.
3. **Process — Normalize & tokenize:** The candidate claim text is normalized and tokenized (`duplicateDetection.ts`).
4. **Process — Duplicate scan:** The candidate is compared via Jaccard similarity against every existing claim's tokenized text.
5. **Decision — $max J(A,B) >= 0.75$?**
   - **Yes →** Block the submission and surface an inline duplicate warning linking to the existing matching claim's page (`/claim/:claimId`). End of this submission's flow; no new document is created.
   - **No →** Proceed to create a new `claims/{claimId}` document with `status: pending`, `verificationCount: 0`, `verifications: []`, `consensusDeadline = createdAt + 7 days`.
6. **Process — Claim enters Verification Queue** (`VerifyQueue.tsx`). Independent verifiers open the claim in `VerifyDetail.tsx`, each contributing a verdict, a source URL, and an explanation; the source-quality rating is not entered by hand but derived automatically from the URL's domain by `determineSourceQuality()`.
7. **Decision — Is `verifications.length >= 3`?**
   - **No →** Claim remains `pending`; loop back to step 6 awaiting more verifiers, *unless* the parallel consensus-deadline sweep (step 8) fires first.
   - **Yes →** Call into the Consensus Engine (`calculateConfidenceScore()`): compute agreement ratio, average reputation, average source quality, and the final weighted confidence score. Set `verdict`, `confidenceScore`, and flip `status` to `verified`.
8. **Parallel process — Consensus-deadline sweep:** Independently of step 7, a periodic check finds any `pending` claim whose `consensusDeadline` has passed with `verificationCount < 3`, computes a confidence score from whatever verifications exist, and force-settles `verdict = CONTESTED`, `status = verified`.
9. **End node — Verified claim:** Submitter is notified; the claim becomes eligible for PNG fact-check card export (Module 6) and rolls into the Analytics Dashboard's aggregations (Module 7).

## 4.3.2 Data Structures

A few design notes worth flagging for the dissertation reader: `Verdict` includes `CONTESTED` as a full member of the enum even though no verifier can directly select it in `VerifyDetail.tsx`'s UI — it is reachable only through the Module 5 consensus-expiry path (see Section 4.1, Section 4.3.1), which is why the type system models it as a `Verdict` (something a claim can ultimately carry) rather than restricting the verifier-facing form to a narrower sub-union. `Claim.verifications` is typed as a plain embedded array (`Verification[]`) rather than a reference to a subcollection, which is the type-level expression of the architectural decision explained in Section 4.2.2. Every optional field marked `?` (`avatarUrl`, `verifiedAt`, `imageUrl`, `verdict`, `confidenceScore`, `agreementRatio`, `avgVerifierReputation`, `sourceQualityScore`, `adminFlagged`, `adminFlaggedAt`, `isAdmin`, `details`, `actionTaken`, `resolvedAt`, `resolvedBy`, `claimId`) reflects a field that only exists once a claim, report, or notification reaches a particular lifecycle stage — TypeScript's strict mode (Chapter 2, Section 2.2) forces every module that reads these fields to explicitly handle the "not yet set" case, which is what prevents, for example, a dashboard chart from crashing on a still-`pending` claim that has no `confidenceScore` yet.

## 4.3.3 Algorithms Design

### Algorithm 1 — Jaccard Duplicate Detection (`src/lib/duplicateDetection.ts`)

**Purpose:** Given an incoming claim's text, decide whether it is a near-duplicate of an already-submitted claim, so the same misinformation forward is never queued for verification twice under slightly different wording.

**Step-by-step:**
1. **Normalize** the input text $T$: lowercase it, strip all non-word/non-whitespace punctuation, and collapse repeated whitespace to single spaces.
   $ "Norm"(T) = "collapseWhitespace"("stripPunctuation"("lowercase"(T))) $
2. **Tokenize** the normalized text into a set of significant words, discarding any token of length $<= 3$ characters (filters out stop-words like "is", "the", "not", "was" that would otherwise dilute the similarity signal):
   $ S_T = { w in "split"("Norm"(T)) | |w| > 3 } $
3. For the incoming claim $A$ and each existing claim $B$ already in the `claims` collection, compute the Jaccard similarity coefficient:
   $ J(A, B) = frac(|S_A inter S_B|, |S_A union S_B|) $
   Implemented directly as an intersection count over `setA`, divided by `setA.size + setB.size - intersection` (the union, computed without materializing it).
4. Track the **best match** — the existing claim with the highest $J(A,B)$ that still clears the threshold. Special cases: if both token sets are empty, similarity is defined as $1$ (identical-triviality case); if exactly one is empty, similarity is $0$.
5. **Decision rule**, with default threshold $tau = 0.75$:
   $ "Action" = cases(
     "Return best-matching claim (block submission, link to it)" & "if" max_(B in "Claims") J(A, B) >= tau,
     "Create new claim, enter Verification Queue" & "otherwise"
   ) $

**Pseudocode:**
```
function findDuplicate(text, existingClaims, threshold = 0.75):
    normalizedInput ← normalize(text)
    bestMatch ← null
    for each claim in existingClaims:
        similarity ← jaccardSimilarity(normalizedInput, claim.text)
        if similarity >= threshold AND (bestMatch is null OR similarity > bestMatch.similarity):
            bestMatch ← { id: claim.id, text: claim.text, similarity }
    return bestMatch   // null ⇒ no duplicate found
```

**Complexity:** $O(n dot m)$ where $n$ is the number of existing claims scanned and $m$ is the average token-set size per claim (set intersection is linear in the smaller set's size). This is acceptable at FactStamp's target scale (a single-institution / campus-deployment demonstration corpus) but would need an inverted-index or approximate-nearest-neighbor structure (e.g. MinHash/LSH) to scale to a web-wide claim corpus — an explicitly acknowledged limitation, not an oversight.

### Algorithm 2 — Weighted Consensus & Confidence Scoring (`src/lib/confidenceScore.ts`)

**Purpose:** Once a claim has accumulated enough independent verifications, synthesize them into a single verdict and a numeric confidence score that reflects not just how many verifiers agreed, but how trustworthy those verifiers and their cited sources are.

**Step-by-step:**
1. Given the claim's verification list $V = {v_1, ..., v_N}$ (triggered once $N >= 3$, per Module 4/5's interaction in Section 4.1), determine the **majority verdict**: group verifications by their `verdict` value, and take the group with the largest count, $N_("majority")$.
2. Compute the **Agreement Ratio** $A$ — the percentage of verifiers who sided with the majority verdict:
   $ A = frac(N_("majority"), N_("total")) times 100 $
3. Compute the **Average Verifier Reputation** $R$ — the mean of each verifier's reputation score (each $R_i in [0,100]$, pulled live from `users/{uid}.reputation` at the moment they voted, per Module 1):
   $ R = frac(1, N) sum_(i=1)^N R_i $
4. Compute the **Average Source Quality Score** $S$ — the mean of each verification's numeric source-quality value (each verification's `sourceQuality` string — `high`/`medium`/`low` — is mapped to a numeric score by `sourceQualityToScore()`: $100$/$70$/$30$ respectively, itself derived from `determineSourceQuality()`'s domain-whitelist classification of the cited `sourceUrl` against known high-quality domains such as `who.int`, `pib.gov.in`, `rbi.org.in` and known medium-quality domains such as major news outlets):
   $ S = frac(1, N) sum_(i=1)^N Q(v_i) $
5. Combine the three components into the final weighted confidence score:
   $ C = (A times 0.40) + (R times 0.30) + (S times 0.30) $
6. **Clamp** $C$ to the valid range $[0, 100]$ and round to the nearest integer (defensive bound-checking even though the weighted sum of three already-bounded $[0,100]$ components cannot mathematically exceed $100$).
7. Assign the claim's final `verdict` to the majority verdict identified in step 1, set `confidenceScore = C`, `agreementRatio = A`, `avgVerifierReputation = R`, `sourceQualityScore = S`, and flip `status` to `verified`.

**Pseudocode:**
```
function calculateConfidenceScore(verifications):
    if verifications.length == 0:
        return { score: 0, agreementRatio: 0, avgReputation: 0, sourceQualityScore: 0 }

    verdictCounts ← groupAndCount(verifications, by = verdict)
    majorityCount ← max(verdictCounts.values())
    agreementRatio ← (majorityCount / verifications.length) * 100

    avgReputation ← mean(v.verifierReputation for v in verifications)
    sourceQualityScore ← mean(v.sourceQuality for v in verifications)   // already numeric 0–100

    score ← round(agreementRatio * 0.40 + avgReputation * 0.30 + sourceQualityScore * 0.30)
    score ← clamp(score, 0, 100)

    return { score, agreementRatio, avgReputation, sourceQualityScore }
```

**Consensus-expiry variant:** The same function is reused, unmodified, by Module 5's 7-day deadline sweep (see Section 4.1) — a `pending` claim whose deadline has passed with fewer than 3 verifications still has `calculateConfidenceScore()` invoked over whatever verifications *do* exist (possibly zero, one, or two), and the resulting verdict is overridden to `CONTESTED` regardless of what the majority-verdict computation returned, since an under-quorum result is definitionally inconclusive. This is a deliberate reuse of the same scoring function rather than a separate expiry algorithm, keeping the confidence-score math consistent whether a claim resolves by quorum or by timeout.
