FactStamp uses **Cloud Firestore**, a NoSQL document-oriented database, as its sole persistence layer — there is no separate relational database or custom REST API. Five top-level collections hold all application state: `users`, `claims`, `notifications`, `reports`, and `audit_logs`. Every collection's shape is defined once in `src/lib/types.ts` (the canonical TypeScript data-model file) and independently re-validated on every write by `firestore.rules`, so the schema below is not merely a design intention — it is mechanically enforced server-side.

## 4.2.1 Schema Design

### Collection: `users`

Verifier and account profile documents, keyed by Firebase Auth `uid`.

| Field | Type | Description | Notes |
|---|---|---|---|
| `uid` | string | Firebase Auth user ID (document ID) | Immutable after creation |
| `displayName` | string | Verifier's display name | Max 100 characters |
| `email` | string | Account email address | Must match `request.auth.token.email` at creation; immutable |
| `avatarUrl` | string (optional) | Profile picture URL | Optional |
| `reputation` | number | Verifier reputation score, 0–100 | Defaults to 50 at signup; only an admin (or the system's own reputation-update logic acting through an admin-equivalent write) can change it thereafter |
| `totalVerifications` | number | Lifetime count of verifications submitted | Defaults to 0; admin-writable only |
| `joinedAt` | string (ISO 8601 timestamp) | Account creation timestamp | Immutable |
| `isAdmin` | boolean (optional) | Staff clearance flag | Defaults to `false`; can only be flipped by an existing admin — a user can never self-promote |

### Collection: `claims`

The central document type — one per submitted claim, with all verifications embedded rather than stored as a subcollection (rationale in Section 4.2.2).

| Field | Type | Description | Notes |
|---|---|---|---|
| `id` | string | Claim document ID | Firestore auto-ID |
| `text` | string | Normalized claim text (typed or OCR-extracted) | 10–2000 characters, enforced server-side |
| `category` | string (enum) | `health` \| `political` \| `religious` \| `financial` \| `other` | Enforced against a fixed whitelist |
| `status` | string (enum) | `pending` \| `verified` | `verified` covers both quorum-reached and consensus-expired (`CONTESTED`) outcomes |
| `createdAt` | string (ISO 8601) | Submission timestamp | Immutable after creation |
| `verifiedAt` | string (optional) | Timestamp the claim reached a final verdict | Set once, on the write that flips `status` to `verified` |
| `consensusDeadline` | string (ISO 8601) | `createdAt` + 7 days | Immutable; drives the consensus-expiry sweep (see Section 4.1, Module 5) |
| `submittedBy` | string | `uid` of the submitting user | Immutable |
| `submittedByName` | string | Display name snapshot at submission time | Max 100 characters; immutable |
| `imageUrl` | string (optional) | Base64 data URI or HTTPS URL of the submitted screenshot | ≤ 800,000 characters (~800 KB); must match `data:image/(jpeg\|png\|webp);base64,` or `https?://` pattern |
| `verdict` | string (enum, optional) | `TRUE` \| `FALSE` \| `MISLEADING` \| `UNVERIFIABLE` \| `CONTESTED` | Set only once the claim resolves |
| `confidenceScore` | number (optional) | Final weighted confidence, 0–100 | Computed by Module 5 (`calculateConfidenceScore()`) |
| `verifications` | array of `Verification` (embedded) | The claim's verification records | See sub-schema below; starts as `[]` |
| `verificationCount` | number | `verifications.length`, denormalized | Must be `0` at creation; must increment by exactly 1 per new-verification write |
| `agreementRatio` | number (optional) | Majority-agreement percentage component of the consensus formula | Denormalized from the last confidence computation |
| `avgVerifierReputation` | number (optional) | Mean verifier reputation component | Denormalized |
| `sourceQualityScore` | number (optional) | Mean source-quality component | Denormalized |
| `adminFlagged` | boolean (optional) | Marks a claim for expedited verifier review | Admin-writable only |
| `adminFlaggedAt` | string (optional) | Timestamp the flag was set | Admin-writable only |

#### Embedded sub-schema: `Verification` (element of `claims.verifications[]`)

| Field | Type | Description | Notes |
|---|---|---|---|
| `id` | string | Verification identifier within the array | Client-generated |
| `claimId` | string | Parent claim ID | Redundant but kept for card/notification rendering convenience |
| `verdict` | string (enum) | `TRUE` \| `FALSE` \| `MISLEADING` \| `UNVERIFIABLE` | A verifier cannot directly cast `CONTESTED` — it is system-assigned only |
| `sourceUrl` | string | Cited source URL | Max 500 characters; must match `^https?://.+` |
| `sourceQuality` | string (enum) | `high` \| `medium` \| `low` | Derived from `determineSourceQuality()`'s domain whitelist |
| `explanation` | string | Verifier's written rationale | 50–1500 characters client-side (see Section 4.5); server enforces 50–3000 |
| `verifierId` | string | `uid` of the verifier | Must equal `request.auth.uid` on write |
| `verifierName` | string | Verifier display name snapshot | Max 100 characters |
| `verifierReputation` | number | Verifier's reputation *at the moment of voting* | Must equal the live value in `users/{uid}.reputation` at write time |
| `createdAt` | string (ISO 8601) | Verification submission timestamp | Immutable |

### Collection: `notifications`

In-app alert documents, one per user event.

| Field | Type | Description | Notes |
|---|---|---|---|
| `id` | string | Notification document ID | Firestore auto-ID |
| `userId` | string | Recipient's `uid` | Immutable; readable only by that user or an admin |
| `type` | string (enum) | `claim_verified` \| `reputation_update` \| `weekly_report` \| `verdict_submitted` | Immutable after creation |
| `title` | string | Short notification heading | Max 200 characters |
| `message` | string | Notification body text | Max 2000 characters |
| `createdAt` | string (ISO 8601) | Creation timestamp | Immutable |
| `isRead` | boolean | Read/unread state | The *only* field a recipient may update on their own notification |
| `claimId` | string (optional) | Related claim, if applicable | Immutable |

### Collection: `reports`

Moderation incident tickets (the Admin Console's "Incident Queue" tab, Section 4.4).

| Field | Type | Description | Notes |
|---|---|---|---|
| `id` | string | Report document ID | Firestore auto-ID |
| `targetType` | string (enum) | `claim` \| `user` \| `verification` | Fixed whitelist |
| `targetId` | string | ID of the reported entity | — |
| `targetTitle` | string | Human-readable label of the target | Max 300 characters |
| `reason` | string (enum) | `misinformation_spam` \| `harassment` \| `low_quality_source` \| `fake_account` \| `manipulation` \| `hate_speech` \| `other` | Fixed whitelist |
| `details` | string (optional) | Reporter's free-text description | Optional in the TypeScript interface, but required by the create rule; max 3000 characters |
| `reportedBy` | string | `uid` of the reporting user | Must equal `request.auth.uid` on create |
| `reportedByName` | string | Reporter display name snapshot | — |
| `reportedAt` | string (ISO 8601) | Submission timestamp | — |
| `status` | string (enum) | `pending` \| `investigating` \| `resolved` \| `dismissed` | Must be `pending` at creation; only an admin can transition it thereafter |
| `severity` | string (enum) | `low` \| `medium` \| `high` | Fixed whitelist |
| `actionTaken` | string (optional) | Admin's resolution note | Admin-writable only |
| `resolvedAt` | string (optional) | Resolution timestamp | Admin-writable only |
| `resolvedBy` | string (optional) | Admin `uid` who resolved the ticket | Admin-writable only |

### Collection: `audit_logs`

Immutable trail of every administrative mutation (the Admin Console's "Audit & Tools" tab, Section 4.4).

| Field | Type | Description | Notes |
|---|---|---|---|
| `id` | string | Log entry ID | Firestore auto-ID |
| `timestamp` | string (ISO 8601) | When the admin action occurred | — |
| `adminId` | string | `uid` of the acting admin | — |
| `adminName` | string | Admin display name snapshot | — |
| `action` | string | Description of the action taken | Max 200 characters |
| `targetType` | string (enum) | `claim` \| `user` \| `report` \| `system` | Fixed whitelist |
| `targetId` | string | ID of the entity acted upon | — |
| `details` | string | Additional context | Max 2000 characters |

## 4.2.2 Data Integrity and Constraints

Every constraint described above is a design *intention* until it is enforced somewhere the client cannot bypass. FactStamp enforces the entire schema server-side via `firestore.rules`, which is read on every single Firestore write attempt — a malicious or buggy client can send whatever payload it likes, but Firestore rejects any write that does not satisfy the matching rule.

**Field-level write validation.** Every `create`/`update` rule in `firestore.rules` inspects `request.resource.data` field-by-field rather than trusting the document as a whole. For example, `claims/{claimId}` creation requires `text.size() >= 10 && text.size() <= 2000`, `category in [...]` against the fixed enum, `status == 'pending'`, `verificationCount == 0`, and `verifications == []` — a client cannot create a claim that is already `verified`, pre-seeded with fake verifications, or outside the text-length bounds.

**The `isAdmin()` helper.** Nearly every privileged write path in the ruleset gates on a single helper function:

```
function isAdmin() {
  return request.auth != null
    && get(/databases/$(database)/documents/users/$(request.auth.uid)).data.get('isAdmin', false) == true;
}
```

This performs a live server-side read of the caller's own `users/{uid}` document at write time — it does not trust any client-supplied claim of admin status. Because `isAdmin` on a `users/{uid}` document can itself only be changed by an existing admin (the self-update branch of the `users` rule explicitly requires `isUnchanged('isAdmin')`), there is no path by which a normal user can grant themselves admin privileges, even by directly calling the Firestore SDK from the browser console. This is the same server-side backstop referenced in Section 4.4/Section 4.5 alongside the client-side `AdminRoute.tsx` dual-layer check.

**Append-exactly-one-verification-per-write.** The most intricate rule in the file governs adding a verification to a claim (Case C of the `claims/{claimId}` update rule). It requires simultaneously that:
- `verificationCount` increases by exactly 1 (`request.resource.data.verificationCount == resource.data.verificationCount + 1`);
- the existing `verifications` array is fully preserved (`request.resource.data.verifications.hasAll(resource.data.verifications)`) — an update cannot silently drop or rewrite a prior verifier's entry;
- the *newly appended element* (indexed at the old array's length) has `verifierId == request.auth.uid` — a verifier can only attach their own identity, never impersonate another verifier;
- that same element's `verifierReputation` exactly matches the caller's *live* `users/{uid}.reputation` value read at write time — a client cannot inflate its own reported reputation to skew Module 5's confidence formula;
- the verdict is restricted to `['TRUE', 'FALSE', 'MISLEADING', 'UNVERIFIABLE']` (a verifier cannot write `CONTESTED` directly — see Section 4.1);
- `sourceUrl` matches `^https?://.+` and is ≤ 500 characters; `explanation` is 50–3000 characters.

This one rule is effectively the server-side mirror of Module 4's client-side `validateVerdictExplanation()` check (see Section 4.5) — the client validation exists for UX (immediate feedback before a round trip), but the Firestore rule is what actually prevents a forged or malformed verification from ever being persisted.

**Immutability rules.** Several fields are permanently frozen once a document is created, enforced via the `isUnchanged(field)` and `identityUnchanged()` helper functions: a claim's `text`, `category`, `submittedBy`, `submittedByName`, `createdAt`, `consensusDeadline`, and `imageUrl` cannot be altered by the "add a verification" or "consensus expiry" update paths (only an admin override, Case A, may touch them, and even then only through the admin's own audited action). `audit_logs` documents disallow `update` and `delete` entirely (`allow update, delete: if false;`) — an audit trail that could itself be edited or erased after the fact would defeat its own purpose.

**Why `verifications[]` is an embedded array, not a subcollection — and the trade-off.** FactStamp deliberately stores verifications as a field on the parent `claims/{claimId}` document rather than as a per-verification subcollection. (`firestore.rules` does still declare a `claims/{claimId}/verdicts/{verdictId}` subcollection — a residue of an earlier design iteration — but no application code reads from or writes to it; every verification in the running system lives in the embedded array.) This choice was made because:
1. **Atomic quorum checks.** Module 5's decision to finalize a verdict the instant the third verification arrives (see Section 4.1) depends on reading `verifications.length` synchronously in the same document snapshot as the write that adds it. A subcollection would require either an extra read (a `.count()` aggregation query) or a denormalized counter kept in sync across two separate writes — introducing a race window between "verification written" and "counter updated" that a quorum-triggering consensus computation cannot tolerate.
2. **Single-read hydration.** Every screen that displays a claim (`ClaimDetail.tsx`, `VerifyDetail.tsx`, the Dashboard's aggregation queries) needs the full verification list alongside the claim metadata; embedding avoids an extra subcollection query per claim view.

The trade-off is real and intentional: Firestore documents are capped at 1 MiB, and an embedded array grows unbounded with the number of verifications a claim ever receives. In practice this is a non-issue for FactStamp's use case — the 3-verifier quorum settles most claims quickly, and even a claim that accumulates dozens of verifications before settling stays orders of magnitude under the 1 MiB ceiling, since each `Verification` element is at most a few KB (bounded by the 3000-character `explanation` cap). A subcollection would become necessary only if the project later supported an unbounded, post-consensus commentary stream — which it deliberately does not.

**The 800 KB image-URI cap.** A submitted screenshot is stored as a base64 data URI directly inside the `claims/{claimId}.imageUrl` field (no Firebase Storage bucket is used — see Chapter 2's zero-cost-infrastructure rationale). Base64 encoding inflates binary size by roughly 33%, and the field must still leave headroom under Firestore's 1 MiB document cap alongside the embedded `verifications[]` array, so `firestore.rules` enforces `imageUrl.size() <= 800000` characters (~800 KB) at the rule layer, on top of client-side compression in `src/lib/imageCompression.ts` that downsizes the image *before* it is ever base64-encoded and sent to Firestore (max dimension 1280 px, JPEG quality stepped down from 0.72 to a floor of 0.4 until the encoded payload is under ~700,000 bytes). A `storage.rules` file is nevertheless deployed alongside the Firestore ruleset, permitting authenticated image uploads under 10 MB to `claim_screenshots/{fileName}` with public read; no application code path currently uses it, so it is a locked-down placeholder rather than part of the live image flow.

**Client cannot be fully trusted — the general principle.** Every one of the client-side checks documented in Section 4.5 (login rate-limiting, XSS sanitization, upload validation, explanation anti-spam checks) exists purely for responsiveness and user experience; none of them is the actual security boundary. A user with browser DevTools open can call the Firestore SDK directly and bypass every client-side check trivially. `firestore.rules` is therefore written to assume exactly that: every constraint that matters for data integrity — the enum whitelists, the length bounds, the ownership checks, the quorum-increment arithmetic, the immutability locks, the admin gate — is duplicated at the rules layer, because that is the one layer the client genuinely cannot circumvent.
