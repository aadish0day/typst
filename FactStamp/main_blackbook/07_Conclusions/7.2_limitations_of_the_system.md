# 7.2 Limitations of the System

FactStamp is a genuinely working system, but honesty about its limitations is part of the dissertation, not an afterthought. The limitations below are real, verified against the current implementation, and grouped by the kind of risk they represent rather than listed in arbitrary order.

## 7.2.1 Coverage & Accuracy Limitations

- **English-only OCR.** The bundled Tesseract.js model (`src/services/ocrService.ts`) only recognizes Latin/English script. A WhatsApp forward written in Devanagari or another regional Indic script cannot be auto-extracted from a screenshot — the submitter must type the claim text manually instead of relying on OCR. Given how much Indian WhatsApp misinformation circulates in Hindi and other regional languages, this materially narrows the population of forwards the system can ingest frictionlessly.
- **Lower OCR accuracy than commercial cloud vision APIs.** Running OCR entirely client-side via WebAssembly was a deliberate privacy and cost trade-off (Section 2.5), but it is still a real accuracy limitation, especially on low-resolution or heavily compressed WhatsApp screenshots, where a cloud vision model such as Google Cloud Vision would extract text more reliably. `cleanExtractedOcrText()` mitigates WhatsApp-chrome noise, and the user can always hand-correct the extracted text, but the underlying recognition quality is capped by what a browser-side WASM model can do.
- **No direct WhatsApp Business API integration.** FactStamp does not intercept or read WhatsApp messages automatically. A user must manually copy-paste text or upload a screenshot into the web app — the system has no chatbot or Business API listener sitting inside WhatsApp itself. This adds a submission-friction step that a native in-app integration would remove.

## 7.2.2 Trust & Governance Limitations

- **Quorum consensus assumes baseline good-faith participation.** The 3-verifier quorum and reputation-weighted confidence score are designed to resist Sybil-style manipulation, but the design still assumes a community of largely good-faith participants. In a small early user base, a coordinated set of adversarial-only accounts could theoretically stack a quorum before organic reputation differentiation has had a chance to down-weight them. Reputation weighting mitigates this risk over time but does not eliminate it, particularly during the platform's early-adoption phase when the pool of verifiers is small.
- **Source-quality scoring depends on a small hardcoded domain list.** `src/lib/confidenceScore.ts` classifies a cited source as high, medium, or low quality using fixed domain lists (e.g., `who.int`, `pib.gov.in` as high-quality; `bbc.com` and similar outlets as medium-quality). Any legitimate, credible source domain that is not on that hardcoded list — a regional newspaper, a specialized medical journal, a state government portal not yet added — defaults to "low" quality by omission, even when it is a genuinely reliable citation. This can unfairly under-weight a valid verification simply because its source domain was never added to the list.

## 7.2.3 Architectural & Scaling Limitations

- **Quorum threshold duplicated as a bare literal across the application layers.** The "3 verifications required" rule is never expressed as a single named constant: it appears as a hardcoded `>= 3` comparison in six separate places across the client-side `ClaimsContext.tsx` and the `firebaseService.ts` service layer. This is a genuine architectural fragility: if the quorum number were ever changed, every one of those locations would need to be updated in lockstep, and a missed update in any one of them would put the queue, the consensus trigger, and the expiry sweep out of agreement with each other. The gap is widened by the fact that `firestore.rules` validates the *shape* of each verification write (Case C of the `claims/{claimId}` update rule) but does not itself enforce the count — so the quorum is, in the end, a client-enforced invariant rather than a server-enforced one.
- **No automated test suite.** `package.json` defines only `dev`, `build`, `preview`, `typecheck`, `emulators` (and its `:persist`/`:export` variants), `seed:db`, `create:admin`, and `create:user` — there is no `test` script and no unit or integration test files anywhere in the codebase. Correctness is currently verified through manual/structured testing rather than a CI-enforced automated suite, which means regressions in core logic (duplicate detection, the consensus formula, security-rule behavior) rely on a human tester noticing them rather than a test pipeline catching them automatically before deployment.
- **Image storage capped by the Firestore-embedded approach.** To stay within the Firebase free tier, uploaded screenshots are compressed and stored as base64 strings directly inside the claim's Firestore document (`src/lib/imageCompression.ts`), rather than in a proper object-storage bucket. This caps usable image payloads at roughly 800 KB per claim and would not scale gracefully to a large volume of images — Firestore document size limits and per-document read costs both work against this approach at scale, even though `storage.rules` already defines a `claim_screenshots` path — currently an unused, locked-down placeholder that no application code path writes to — which could carry that load if the flow were migrated to use it as the primary path.
