## 3.6.1 Entity-Relationship (E-R) Diagram

The ER diagram models FactStamp's Firestore data domain as five conceptual entities: **USER** (uid, displayName, reputation, isAdmin), **CLAIM** (id, text, status, verdict, confidence, category, submittedBy), **VERIFICATION** (id, claimId FK, verifierId FK, verdict, sourceUrl, sourceQuality), **DUPLICATE_CLUSTER** (canonical claim grouping for claims matched above the 0.75 Jaccard threshold), and **CATEGORY_METRIC** (aggregated per-category rollup counts feeding the analytics dashboard). USER submits many CLAIMs and casts many VERIFICATIONs; CLAIM receives many VERIFICATIONs (minimum 3 for quorum) and may group many near-duplicate submissions under a DUPLICATE_CLUSTER; CLAIM aggregates many-to-one into a CATEGORY_METRIC. The full entity attribute list and cardinality matrix for this diagram is already worked out in `Rules/Diagrams-Checklist.md` the "Entity-Relationship (E-R) Diagram" and will be reused verbatim for the compiled PlantUML source.

## 3.6.2 Class Diagram

The class diagram models FactStamp's core domain classes in object-oriented terms, independent of the specific React/TypeScript implementation: an abstract `BaseVerifier` class (id, reputation, `submitVerdict()`) specialized by a concrete `CommunityVerifier` class (FactStamp has no separate verifier role — every registered user is a `CommunityVerifier`); a `Claim` class (text, status, category, `addVerification()`) composed of many `Verification` objects (verdict, sourceUrl, sourceQuality, rationale); and a `ConsensusEngine` class exposing the weighted-scoring method that consumes a `Claim`'s verification set to produce a settled verdict and confidence score. Composition (`Claim` *-- `Verification`) reflects that verifications cannot exist independent of their parent claim, matching Firestore's embedded-array denormalization decision (Chapter 2 Section 2.9).

## 3.6.5 Activity Diagram

The activity diagram traces the full claim lifecycle as a control-flow swimlane: a user submits text or a screenshot → (if screenshot) OCR extraction and WhatsApp-chrome cleanup runs → the duplicate-detection engine computes Jaccard similarity against the existing corpus → a decision branch either redirects to an existing verified claim (J ≥ 0.75) or creates a new pending claim → the new claim enters the verification queue and accumulates verifications one at a time → a second decision branch checks whether quorum (≥3) has been reached or the 7-day deadline has expired → on either branch exit, the consensus engine computes the final verdict and confidence score → the claim becomes eligible for card export. This is the single most useful diagram for explaining FactStamp's end-to-end behavior to a non-technical reader.

## 3.6.6 State Diagram (State Machine)

The state diagram models a `Claim`'s lifecycle as a finite state machine over the two status values the implementation actually defines (`ClaimStatus = 'pending' | 'verified'` in `src/lib/types.ts`): `[*] → pending` (on creation), then either `→ verified` carrying the majority verdict (once the third verification arrives and `verificationCount >= 3`) or `→ verified` carrying the verdict `CONTESTED` (if the 7-day `consensusDeadline` passes while `verificationCount < 3`). `verified` is the terminal state `→ [*]`; note that `CONTESTED` is a *verdict* value, not a separate status. Verifications accumulating below quorum are shown as a self-transition on `pending` rather than a distinct "under review" state, matching the transition triggers implemented in `ClaimsContext.tsx`'s `computeUpdatedClaim()` and `expireOverdueClaims()`.

## 3.6.7 Sequence Diagram

The sequence diagram traces the temporal message flow for a single verification-to-consensus event: `Verifier` → `VerifyDetail (UI)` → `ClaimsContext` (submit verdict) → `firebaseService` (persist verification, increment `verificationCount`) → `firestore.rules` (server-side validation) → back to `ClaimsContext`, which — if `verificationCount >= 3` — invokes `confidenceScore.ts`'s `calculateConfidenceScore()`, receives the computed verdict/confidence, persists the settled claim, and finally triggers `NotificationsContext` to notify the original submitter. ## 3.6.8 Package Diagram

The package diagram groups FactStamp's source tree into cohesive architectural packages: a `pages` package (route-level views), a `components` package (with a nested `components/ui` primitive-component package), a `contexts` package (the five React Context providers: Auth, Claims, Notifications, Theme, Users), a `lib` package (pure utility/algorithm modules: `duplicateDetection.ts`, `confidenceScore.ts`, `security.ts`, `types.ts`), and a `services` package (`firebaseService.ts`, `ocrService.ts`) — with dependency arrows showing that `pages` depends on `contexts`, `contexts` depends on `services` and `lib`, and `services` depends on `lib` (e.g. `firebaseService.ts` uses the shared `types.ts` contracts), never the reverse.

## 3.6.11 Data Flow Diagrams (Level 0, Level 1, Level 2)

**Level 0 (Context Diagram):** models FactStamp as a single process bubble ("0. FactStamp System") with two external entities — **User** (submits claims, casts verifications, receives notifications) and **Admin** (moderates data, views audit logs) — and Firestore/Firebase Auth as an external data store shown at the boundary.

**Level 1:** decomposes the single Level 0 process into FactStamp's major processing stages as separate numbered bubbles: 1.0 Submit Claim, 2.0 Detect Duplicate, 3.0 Manage Verification Queue, 4.0 Compute Consensus, 5.0 Generate Fact-Check Card, 6.0 Serve Analytics Dashboard, and 7.0 Admin Moderation — each reading from and writing to the shared Firestore data store (`D1 Claims` — which carries its verifications as an embedded array rather than a separate store — `D2 Users`, `D3 Reports`, `D4 Audit Logs`).

**Level 2 (drill-down of 1.0 Submit Claim, the most complex Level 1 process):** further decomposes claim submission into 1.1 Accept Text/Screenshot Input, 1.2 Compress Image, 1.3 Run Client-Side OCR, 1.4 Clean WhatsApp Chrome Text, 1.5 Auto-Classify Category, and 1.6 Persist Claim Record — tracing exactly the Module 2 pipeline described in Section 3.5.

## 3.6.12 Event Table

Per `Rules/Diagram-rules.md` Rule 4, the Event Table is tabular data, not a diagram, and is rendered here as a genuine table (to be reproduced with `styled-table()` in the compiled Typst chapter).

| Trigger | Source | Action / Process | Output | Destination |
|---|---|---|---|---|
| Claim submitted (text or screenshot) | User (Submit page) | Module 2 ingests input; if screenshot, runs client-side OCR extraction and WhatsApp-chrome cleanup; Module 3 computes Jaccard similarity against existing claims | New claim record (if unique) or a redirect reference (if duplicate) | Firestore `claims` collection / User's browser (redirect) |
| Duplicate match found (J ≥ 0.75) | Duplicate Detection Engine (Module 3) | Suppress new claim creation; resolve to existing canonical claim | Redirect payload pointing to existing `claimId` | User's browser (Claim Detail page) |
| Verification submitted | Community Verifier (Verify Detail page) | Module 4 validates one-vote-per-user and anti-self-verification rules; persists verdict, source URL, source quality, and explanation; increments `verificationCount` | Updated `Verification` record appended to claim | Firestore `claims` collection (embedded verifications array) |
| Consensus reached (verificationCount ≥ 3, majority settled) | Weighted Consensus Engine (Module 5) | Compute `Confidence = 0.40×AgreementRatio + 0.30×AvgVerifierReputation + 0.30×SourceQualityScore`; determine final verdict; update reputations (+2 majority-aligned, -1 dissenting) | Settled `verdict`, `confidenceScore`, and updated verifier `reputation` values | Firestore `claims` and `users` collections; Notifications system |
| Consensus deadline expired (7 days, `verificationCount < 3`) | Consensus-Deadline Scheduler (`ClaimsContext.tsx`, `expireOverdueClaims()`) | Auto-settle the claim: move `status` from `pending` to `verified` and set `verdict = CONTESTED`; skip reputation adjustment | Claim `status = verified`, `verdict = CONTESTED` | Firestore `claims` collection; Notifications system |
