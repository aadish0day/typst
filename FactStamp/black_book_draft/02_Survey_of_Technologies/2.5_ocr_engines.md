# 2.5 OCR Engines

This is one of the project's most consequential technology decisions, so it is treated as its own survey rather than a single-line library pick.

## 2.5.1 The Alternatives

A WhatsApp forward frequently arrives as a screenshot rather than plain text, so some form of Optical Character Recognition is required to extract the claim text before it can be normalized, deduplicated, or queued for verification. Three broad approaches exist:

- **Cloud vision/OCR APIs** (Google Cloud Vision, AWS Textract) — mature, high-accuracy managed services that accept an image over HTTPS and return extracted text. They require sending the image to a third-party server and charge per request.
- **LLM vision endpoints** (e.g., a multimodal model's image-understanding API) — can extract text and, further, could plausibly attempt to interpret or summarize the claim in the same call. Also a paid, cloud-hosted, per-request service, with the same data-egress profile as the above.
- **Client-side WebAssembly OCR** (Tesseract.js) — runs the OCR engine entirely inside the browser via WASM, with no network call and no per-request cost.

## 2.5.2 FactStamp's Choice — Tesseract.js 7.0, Client-Side

Rather than sending a user's WhatsApp forward screenshot to a cloud OCR/vision API, FactStamp runs Tesseract.js entirely inside the browser via WebAssembly (`src/services/ocrService.ts`, `createWorker` from `tesseract.js`). This decision was driven by three factors:

1. **Privacy.** A screenshot of a WhatsApp forward often contains other participants' names and phone numbers in the chat header. Never transmitting that image off-device avoids an entire category of data-handling and consent concerns that a cloud API would introduce — FactStamp does not need a data-processing agreement with a third party for content it never sends them.
2. **Cost.** Cloud OCR/vision APIs charge per request; at any meaningful submission volume, this becomes a recurring operational cost the project has no revenue model to cover. Client-side WASM OCR is free at unlimited scale — a direct match for the project's zero-infrastructure-cost constraint (see Section 2.1).
3. **Offline capability.** Once the Tesseract WASM core and the English language model are cached by the browser, OCR extraction continues to work without a network round-trip, which also means OCR latency does not depend on a third-party API's availability or response time.

## 2.5.3 The Honest Trade-off

The cost of this choice is lower raw accuracy than a modern cloud vision model, especially on low-resolution or heavily-compressed screenshots — a WhatsApp forward that has already been re-compressed through several forwarding hops is exactly the worst case for any OCR engine, client-side or cloud. This is mitigated two ways rather than ignored:

- `cleanExtractedOcrText()` is a WhatsApp-chrome-specific regex cleanup pass that strips timestamps, delivery checkmarks, and carrier/battery status-bar text that Tesseract otherwise mis-recognizes as part of the message body.
- The user can always manually correct the extracted text before submission — OCR output is a starting draft, never the final claim text FactStamp acts on.

Choosing accuracy-for-privacy-and-cost here is consistent with the rest of the stack: FactStamp repeatedly trades a small amount of best-in-class capability for zero operating cost and zero third-party data exposure, and the OCR layer is the clearest single example of that trade-off in the whole codebase.
