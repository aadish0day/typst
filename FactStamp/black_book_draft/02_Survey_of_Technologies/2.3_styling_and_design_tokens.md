# 2.3 Styling and Design Tokens

## 2.3.1 Tailwind CSS v4

Tailwind v4's new `@tailwindcss/vite` plugin — CSS-native configuration, with no separate `tailwind.config.js` file and no PostCSS pipeline to maintain — was adopted for its OKLCH-based design-token system, which underlies the entire "warm editorial" visual language documented in the project's `DESIGN.md`: a warm-cream background palette, saffron brand accents, and five verdict-semantic colors (True / False / Misleading / Unverifiable / Contested), each double-encoded with an icon so verdict meaning never depends on color alone. Compared to Styled-Components or plain CSS Modules, Tailwind's utility-first approach keeps styling co-located with markup and produces zero-runtime CSS (no client-side style computation, unlike CSS-in-JS libraries), while the v4 CSS-native configuration removes the JavaScript build-time configuration step v3 required.

## 2.3.2 Why OKLCH Over Traditional Color Spaces

OKLCH (Lightness, Chroma, Hue in the Oklab perceptual color space) was chosen over `rgb()`/`hsl()` because it is perceptually uniform — a given step change in the lightness channel produces a visually consistent brightness change across every hue, which is what makes it possible to generate an entire color ramp (e.g., ten shades of the saffron brand color) programmatically and have every step look evenly spaced to the eye. `hsl()` cannot make this guarantee — identical lightness values at different hues can look wildly different in perceived brightness. This property is what makes Tailwind v4's OKLCH-native token system valuable for a project with a deliberately curated warm palette rather than an incidental side effect.

The trade-off is that `oklch()`/`oklab()` are relatively new CSS Color Level 4 functions, and not every rendering pipeline understands them — a fact that becomes directly relevant later in this chapter (§2.6), where it is the reason a legacy canvas-based card export parser had to be replaced entirely.

## 2.3.3 Utility Class Composition — `clsx` + `tailwind-merge`

Conditional Tailwind class construction (e.g., a button component that applies different utility classes depending on its `variant` and `disabled` props) can easily produce class-string conflicts, where two conditionally-applied classes both target the same CSS property and the wrong one wins based on source order. `clsx` (conditional class-name construction) composed with `tailwind-merge` (which understands Tailwind's utility namespaces and resolves conflicts by keeping the last conflicting utility rather than concatenating both) is wrapped in a single `cn()` helper in `src/lib/utils.ts`, used across the entire component library to resolve conditional class conflicts cleanly rather than relying on CSS specificity accidents.
