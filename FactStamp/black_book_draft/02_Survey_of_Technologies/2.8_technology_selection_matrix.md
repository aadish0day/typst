# 2.8 Technology Selection Matrix

## 2.8.1 Core Technology Comparison Summary

| Concern | Chosen Technology | Rejected Alternative | Reason |
|---|---|---|---|
| Application Architecture | React SPA + Firebase BaaS | SSR/hybrid framework (Next.js) + custom Node server | No server-runtime budget; Firestore `onSnapshot` covers all real-time needs natively. |
| UI Framework | React 18.3.1 | Vue 3 / Svelte | Ecosystem maturity for Firebase bindings; Context API sufficient for a shallow, 5-concern state graph. |
| Type Safety | TypeScript 5.5 (strict) | Plain JavaScript | Compile-time safety against malformed/legacy Firestore document shapes. |
| Build Tooling | Vite 5.4 | Create React App (deprecated) / hand-rolled Webpack | Native ESM dev server, near-instant HMR, manual vendor chunk-splitting. |
| Styling | Tailwind CSS v4 (OKLCH tokens) | Styled-Components / CSS Modules | Zero-runtime CSS; OKLCH perceptual-uniformity design-token system. |
| Animation | Framer Motion 12 | CSS-only transitions | JS-driven orchestration needed for staggered reveals and spring-physics panel mounts. |
| Backend | Firebase v12 (BaaS) | Custom Node/Express + PostgreSQL | No dedicated server/DevOps budget; native real-time listeners; declarative server-side authorization via Security Rules. |
| Database Schema (verifications) | Embedded array on claim document | Separate `verifications` subcollection | Single-read claim reconstruction avoids N+1 reads in list views; verification count is small and bounded. |
| OCR | Tesseract.js 7.0 (client-side WASM) | Google Cloud Vision / AWS Textract / LLM vision API | Zero cost, zero data egress, offline-capable; trade-off is lower accuracy, mitigated by manual correction. |
| Card Rasterization | `html-to-image` (SVG foreignObject) | Hand-written canvas parser / `html2canvas` | Native OKLCH/OKLAB CSS Color 4 support via browser-native rendering, not a custom CSS parser. |
| Consensus Model | Weighted quorum consensus (3-verifier minimum, 40/30/30 formula) | Single-moderator editorial / simple majority vote / BFT distributed consensus | Combines quorum-floor trust with evidence-quality and reputation weighting; BFT has no native concept of source credibility. |
| Duplicate Handling | Jaccard token-similarity pre-filter (J ≥ 0.75) | No pre-filtering / exact-string matching | Prevents redundant quorum queues for reworded duplicates of the same viral forward. |
| Hosting | Firebase Hosting / Vercel / Docker + Nginx | AWS / bare-metal VPS | Zero-ops static hosting matching the BaaS backend; Docker kept as an on-prem escape hatch. |

## 2.8.3 Reading the Matrix

Two patterns recur across nearly every row of §2.8.1, and both trace back to the architectural choice made in §2.1:

1. **Zero-server-cost is the dominant constraint.** Firebase BaaS, Firestore's embedded-array schema, client-side OCR, and the zero-ops static hosting targets are all instances of the same underlying decision — push cost and computation to the client and to managed services rather than to an operated server the project would have to pay for and maintain.
2. **"Native browser behavior over custom reimplementation" is the recurring engineering principle.** `html-to-image`'s foreignObject strategy over a hand-written CSS parser, and Firestore Security Rules as a declarative authorization layer over hand-rolled middleware, both reflect a preference for delegating to a platform's own correct implementation rather than maintaining a parallel one that can drift out of sync — the same lesson the legacy canvas-parser failure (§2.6.2) taught the hard way.

The consensus-model choice in §2.7 stands somewhat apart from the rest of the table: it is not a cost-minimization decision like the others, but the one place in this chapter where the technology choice *is* the product's core value proposition, rather than infrastructure supporting it.
