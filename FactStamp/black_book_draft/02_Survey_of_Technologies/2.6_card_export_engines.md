# 2.6 Card Export Engines

## 2.6.1 The Alternatives

Turning a styled DOM element (the fact-check card component) into a downloadable PNG image is a well-known problem in web development with three common solution shapes:

- **Raw HTML5 Canvas API** — manually redraw every visual element (text, shapes, gradients) onto a `<canvas>` element using imperative drawing calls. Gives complete control but requires re-implementing a layout and CSS-parsing engine by hand for anything beyond the simplest static shapes.
- **`html2canvas`** — a widely-used library that walks the DOM and reads computed styles, then attempts to redraw the equivalent visuals onto a canvas using its own internal CSS interpretation logic. This spares the developer from hand-drawing every element, but the library still ships its own CSS parser, which lags behind the browser's own and can fail on newer CSS syntax.
- **`html-to-image`** — instead of reimplementing CSS parsing, it serializes the target DOM subtree into an SVG `<foreignObject>`, which the *browser's own* rendering engine then paints, and rasterizes the result to a canvas/PNG. Because the browser itself does the styling work, this approach inherits whatever CSS support the browser already has — including brand-new syntax — with zero additional parsing logic to maintain.

## 2.6.2 FactStamp's Choice — `html-to-image`, After a Legacy Canvas Parser Failed

The shareable fact-check card (`src/components/FactCheckCard.tsx`) is rasterized client-side via `html-to-image`, but this was not the project's first attempt. FactStamp originally used a hand-written, canvas-based CSS parser to generate the card image, and that parser failed in production: it could not interpret the `oklch()`/`oklab()` color functions used throughout the Tailwind v4 design tokens (see Section 2.3), because it implemented its own limited CSS color-value interpreter rather than delegating to the browser. The result was broken, black, or incorrectly-colored card exports for a design system built entirely on OKLCH.

`html-to-image` was adopted specifically to eliminate this class of bug rather than to patch around it. Because it uses the browser's native SVG `<foreignObject>` rendering path, it resolves CSS Color Level 4 syntax exactly as the browser itself does — there is no separate color-parsing logic in the library at all to fall behind the CSS spec. This produces crisp 1080 px-wide PNG exports (a 540 CSS px card rasterized at 2× device-pixel-ratio, its height determined by the card's own content rather than fixed to a square) with zero layout distortion, matching what the user actually sees on screen rather than an approximation of it.

`html2canvas` was considered and rejected for the same underlying reason the legacy parser failed: it ships its own CSS interpretation layer rather than delegating to the browser, so it carries the same structural risk of falling behind new CSS syntax (OKLCH included) that just broke the legacy implementation. Choosing `html-to-image`'s foreignObject strategy was a decision to stop maintaining any custom CSS-interpretation code at all, not merely to switch to a marginally more capable version of it.
