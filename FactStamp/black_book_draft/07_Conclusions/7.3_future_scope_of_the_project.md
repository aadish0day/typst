# 7.3 Future Scope of the Project

The limitations identified in Section 7.2 map directly onto a concrete roadmap rather than open-ended wishful features. The items below are organized into near-term work (extending or hardening what already exists) and long-term work (larger architectural or platform changes), each with a reason it would matter.

## 7.3.1 Near-Term Scope

- **Multi-language OCR (Devanagari and other Indic scripts).** Extending the Tesseract.js pipeline with additional trained language models would directly address the English-only OCR limitation (Section 7.2.1) and open the system to the large volume of Hindi and regional-language WhatsApp forwards that currently require manual transcription — this is arguably the single highest-impact near-term change given how much Indian misinformation circulates outside English.
- **Expanding the source-quality domain list into a maintained, community-curatable credibility database.** Rather than a small hardcoded high/medium/low domain list in `confidenceScore.ts`, a maintained and community-extensible credibility database would let legitimate regional or specialized sources be added over time instead of defaulting to "low quality" by omission — this directly closes the source-quality gap identified in Section 7.2.2 without requiring a redesign of the confidence formula itself.
- **Consolidating the quorum threshold into a single source of truth.** Refactoring the hardcoded `>= 3` checks that currently sit as bare literals in the client Context and the service layer into a single shared constant (or a Firestore-remote-config value read by every layer, including the security rules) would remove the architectural fragility flagged in Section 7.2.3 and make any future quorum-size change (e.g., raising it as the platform scales) a one-line change instead of a six-location, easy-to-desynchronize edit. Promoting the same value into `firestore.rules` would additionally turn the quorum from a client-enforced invariant into a server-enforced one.
- **An appeal / re-review workflow for CONTESTED claims.** Claims that expire into `CONTESTED` after the 7-day consensus deadline currently have no path back into active review. A structured re-review or appeal flow would give genuinely ambiguous claims a second pass with fresh verifiers, rather than leaving them permanently unresolved — this matters because a claim stuck as `CONTESTED` provides no more clarity to the public than no fact-check at all.
- **A basic automated test suite.** Adding unit tests for the two most consequential pieces of logic — the Jaccard duplicate-detection threshold and the weighted consensus formula — plus integration tests against the Firebase Local Emulator Suite (already used for `npm run emulators`) would close the gap flagged in Section 7.2.3 and let regressions in core scoring logic be caught before deployment rather than by a human noticing incorrect verdicts in production.

## 7.3.2 Long-Term Scope

- **WhatsApp Business API / chatbot-based direct submission.** Integrating with the WhatsApp Business API so a user could forward a suspicious message directly to a FactStamp bot number, rather than manually copying text or uploading a screenshot into the web app, would remove the submission-friction step identified in Section 7.2.1 and meet users inside the exact medium the misinformation is already traveling through.
- **Migrating large images to Firebase Storage as the primary flow.** The `storage.rules` file already defines a `claim_screenshots` path, but no application code path writes to it, and the primary image flow still compresses screenshots to base64 inside Firestore documents. Migrating to Storage-backed images as the default (rather than leaving that rule as an unused placeholder) would remove the roughly 800 KB per-claim image cap and let the platform scale to a much larger image volume without hitting Firestore document-size or read-cost constraints.
- **A mobile app wrapper (React Native or installable PWA).** Packaging the existing web application as an installable Progressive Web App, or a thin React Native wrapper, would give FactStamp a persistent home-screen presence and access to native push notifications, which matters because most WhatsApp forwarding happens from a phone, not a desktop browser tab that has to be reopened.
- **A browser extension for one-click submission.** A companion browser extension that lets a user right-click any webpage or chat screenshot and submit it to FactStamp directly, without navigating to the web app first, would reduce submission friction for the growing share of misinformation that first surfaces on the open web before being forwarded into WhatsApp groups.
- **Push notifications (web push) instead of only in-app notifications.** Currently, a submitter learns their claim reached consensus only by returning to the app. Web push notifications would close that loop proactively, which matters for the core objective of getting a verified debunk back into circulation as quickly as possible after consensus is reached.
- **Multi-tenant support for other messaging platforms (Telegram, SMS forwards).** The underlying submission, duplicate-detection, and quorum-consensus pipeline is not conceptually WhatsApp-specific — extending claim ingestion to Telegram forwards or SMS-based chain messages would let the same verification infrastructure serve other closed, forward-driven misinformation channels that share WhatsApp's structural problem of being invisible to search-engine-indexed fact-checking.
