# 4.6 Test Cases Design

*(Draft status: content-complete narrative in Markdown. Test conditions are derived directly from the constraints documented in Section 4.2.2 and Section 4.5, so every expected result traces to an actual enforced rule rather than an assumed one. The table below is rendered in the compiled Typst chapter using the `styled-table()` helper.)*

---

The test cases below cover the core functional pipeline (registration → submission → duplicate detection → verification → consensus) and the security-critical paths (rate-limited login, admin access control) that Chapters 4.2, 4.4, and 4.5 describe. Full execution logs and pass/fail results belong to Chapter 5 (Implementation and Testing) / Chapter 6 (Results and Discussion); this section defines the **design** of the test cases themselves.

| Test ID | Module | Test Condition | Input | Expected Result |
|---|---|---|---|---|
| TC-01 | Auth (Module 1) | New user registers with valid email/password | Valid email, password of 8+ characters containing at least 1 uppercase letter and 1 digit, display name ≥ 2 characters | Account created; `users/{uid}` document seeded with `reputation: 50`, `totalVerifications: 0`, `isAdmin: false` |
| TC-02 | Auth (Module 1) | User logs in with valid credentials | Correct email + password | Session established; redirected to intended page; login attempt counter reset via `resetLoginAttempts()` |
| TC-03 | Auth (Module 1) | User logs in with invalid credentials | Incorrect password, valid email | Login rejected; error shown; `recordFailedLogin()` increments the attempt counter for that identifier |
| TC-04 | Auth / Security (Module 1, 8) | User exceeds login attempt limit | 5 consecutive failed login attempts against the same identifier | 6th attempt blocked; `checkLoginRateLimit()` returns `isLockedOut: true`; UI shows remaining lockout time via `formatLockoutRemaining()` (15:00 counting down) |
| TC-05 | Ingestion (Module 2) | User submits a claim as plain text | Text, 20–500 characters (the `Submit.tsx` bound, which sits inside the server rule's wider 10–2000 range), valid category | Claim created with `status: pending`, `verificationCount: 0`, `verifications: []`, `consensusDeadline` = now + 7 days |
| TC-06 | Ingestion / OCR (Module 2) | User submits a claim via WhatsApp screenshot | Valid JPEG/PNG screenshot ≤ 5 MB | Image compressed and OCR-extracted via Tesseract.js; WhatsApp chrome (timestamps, checkmarks) stripped by `cleanExtractedOcrText()`; extracted text shown for user review before submission |
| TC-07 | Duplicate Detection (Module 3) | New submission closely matches an existing claim | Text with $J(A,B) >= 0.75$ against an existing claim's tokens | Submission blocked (Submit button disabled); inline duplicate warning links to the existing claim's `/claim/:claimId` page; no new `claims` document created |
| TC-08 | Duplicate Detection (Module 3) | New submission is sufficiently distinct from all existing claims | Text with $max J(A,B) < 0.75$ against every existing claim | New `claims` document created; claim enters the Verification Queue |
| TC-09 | Verification Queue (Module 4) | Verifier submits a verdict below quorum | 1st or 2nd verification on a claim, valid verdict/source/explanation | Verification appended to `verifications[]`; `verificationCount` incremented by exactly 1; `status` remains `pending`; no verdict/confidenceScore assigned yet |
| TC-10 | Verification Queue (Module 4) | Verifier submits an explanation that fails anti-spam validation | Explanation < 50 characters, or repeated-character spam (`"aaaaaa"`), or a copy of the claim text | `validateVerdictExplanation()` rejects the submission client-side with a specific error; no Firestore write attempted |
| TC-11 | Verification Queue / Consensus (Module 4, 5) | Verification reaches exactly quorum | 3rd verification submitted on a claim | `calculateConfidenceScore()` invoked; majority verdict determined; `confidenceScore`, `agreementRatio`, `avgVerifierReputation`, `sourceQualityScore` set; `status` flips to `verified` |
| TC-12 | Consensus Engine (Module 5) | Claim remains under quorum past its deadline | `verificationCount < 3` and `consensusDeadline` has elapsed | Consensus-expiry sweep force-settles the claim: `verdict = CONTESTED`, `status = verified`, confidence computed from the available (fewer than 3) verifications |
| TC-13 | Admin (Module 8 / Admin Console) | Admin overrides a claim's verdict | Admin authenticated; claim ID; new verdict/confidence value via Claims Moderation tab | Claim document updated (Case A of the `claims` update rule); action recorded in `audit_logs` via `addAuditLog()` |
| TC-14 | Security / Admin Access Control | Unauthenticated or non-admin user attempts to access `/admin` | Direct navigation to `/admin` without a valid admin session, or with `fs_admin_session_unlocked` forged via DevTools but `isAdmin !== true` | Login gate shown; forged session flag discarded (`sessionStorage.removeItem`) since `hasVerifiedAdminRole` re-derives from the live Firestore `isAdmin` field, not the flag; access denied |
| TC-15 | Data Integrity / `firestore.rules` | Client attempts to forge a verification's reputation value | Direct Firestore SDK write with `verifierReputation` set higher than the caller's actual `users/{uid}.reputation` | Write rejected server-side — the rule requires the appended verification's `verifierReputation` to exactly equal the live value read from the caller's own profile |
| TC-16 | File Upload Validation (Module 2, 8) | User uploads a disguised non-image file | A `.exe` file renamed to `photo.png` with a spoofed `image/png` MIME type | Extension and MIME checks pass, but magic-byte signature check fails (`validateImageUpload()`); upload rejected with "file content does not match a valid image format" |
