FactStamp is decomposed into **8 core system modules**, each traceable to real source files in the codebase (`/home/aadish/Documents/Github/FactStamp`). Chapter 3.5 (Preliminary Product Description) introduced these modules at a summary level; this section documents each module's internal responsibilities, key functions, and — critically — how the modules call into one another to form the end-to-end claim lifecycle (submission → duplicate check → verification queue → consensus → shareable card → analytics), with Module 8 (Security & Notifications) cutting across all of the above.

## Module 1 — Authentication & Verifier Reputation

**Core files:** `src/contexts/AuthContext.tsx`, `src/pages/SignIn.tsx`, `src/pages/SignUp.tsx`, `src/services/firebaseService.ts`.

`AuthContext.tsx` wraps the Firebase Auth SDK in a React Context so that every screen in the app can read the current session (`user`, `isLoading`) and call `signIn`, `signUp`, `signInWithGoogle`, `signOut`, and `updateUser` without touching the Firebase SDK directly. Registration supports both email/password and Google OAuth. On first sign-up, `firebaseService.ts` creates a `users/{uid}` Firestore document seeded with `reputation: 50` (the midpoint of the 0–100 scale — new verifiers start neither trusted nor untrusted), `totalVerifications: 0`, and `isAdmin: false`. This base value is enforced server-side too: `firestore.rules` only allows a self-created `users/{uid}` document if `reputation == 50` and `totalVerifications == 0`, so a user cannot self-provision an inflated reputation at signup.

Every other module depends on Module 1: Module 2 (Submission) requires an authenticated `uid` to attach to a claim as `submittedBy`; Module 4 (Verification Queue) requires an authenticated `uid` to attach a verification as `verifierId`; Module 5 (Consensus Engine) reads each verifier's *current* `reputation` value out of their `users/{uid}` document at the moment they vote, which is what makes the reputation feedback loop (§4.3.3) actually connect back into every verdict's confidence score.

## Module 2 — Forward Submission / Ingestion & OCR

**Core files:** `src/pages/Submit.tsx`, `src/services/ocrService.ts`, `src/lib/imageCompression.ts`.

`Submit.tsx` accepts a claim in either of two forms: raw pasted text, or an uploaded WhatsApp forward screenshot. A screenshot first passes through `src/lib/imageCompression.ts` (client-side Canvas-based downscaling and re-encoding, keeping the final base64 payload under the 800 KB Firestore field cap — see §4.2.2), then through `ocrService.ts`, which spins up a Tesseract.js WebAssembly worker (`createWorker`) entirely in the browser — no image ever leaves the client. The raw OCR output is passed through `cleanExtractedOcrText()`, a WhatsApp-chrome-specific regex cleanup pass that strips timestamps, delivery/read checkmarks, carrier signal and battery-status-bar text, and other UI chrome that Tesseract otherwise transcribes as if it were claim content. The user is always shown the cleaned text and can manually correct it before final submission, which is the project's explicit mitigation for OCR's lower raw accuracy versus a cloud vision API (see Chapter 2, §2.7).

Once the submitter confirms the text, `Submit.tsx` calls forward into **Module 3 (Duplicate Detection)** before a new `claims/{claimId}` document is ever created — submission is gated on the duplicate check, not the other way around.

## Module 3 — Duplicate Detection Engine

**Core file:** `src/lib/duplicateDetection.ts`.

This module implements token-level Jaccard similarity. The incoming claim text and every existing claim's text are normalized (`normalize()`: lowercased, punctuation stripped, whitespace collapsed) and tokenized into sets of words longer than 3 characters (`tokenize()` — short stop-words like "is", "the", "not" are deliberately excluded so they cannot inflate a false-positive similarity score). `jaccardSimilarity(a, b)` then computes

$ J(A, B) = frac(|S_A inter S_B|, |S_A union S_B|) $

against every existing claim, and `findDuplicate()` returns the single best match whose similarity is $>= 0.75$ (the exported `threshold` default). If a match is found, `Submit.tsx` blocks the submission (the Submit button is disabled) and raises an inline duplicate warning carrying a direct link to the existing claim's `/claim/:claimId` page, so no new document is created — this is what prevents the Verification Queue (Module 4) from ever being asked to re-adjudicate a claim the community has already resolved. If no match clears the threshold, `Submit.tsx` proceeds to create a new `claims/{claimId}` document with `status: 'pending'`, `verificationCount: 0`, and `verifications: []`, and the claim enters Module 4's queue.

## Module 4 — Verification Queue

**Core files:** `src/pages/VerifyQueue.tsx`, `src/pages/VerifyDetail.tsx`, `src/contexts/ClaimsContext.tsx`.

`VerifyQueue.tsx` lists every `pending` claim (admin-flagged claims are surfaced first, per `adminFlagged`/`adminFlaggedAt`). `VerifyDetail.tsx` is the individual verifier's workbench: the verifier reads the claim, selects a verdict (`TRUE` / `FALSE` / `MISLEADING` / `UNVERIFIABLE` — a verifier cannot directly cast `CONTESTED`, which is a system-assigned terminal state, see Module 5), supplies a `sourceUrl`, and writes a plain-language `explanation`. Before the submission is accepted, the explanation is run through `validateVerdictExplanation()` in `src/lib/security.ts` — minimum 50 characters and 8 words, with anti-spam checks (repeated characters, repeated words, generic cop-out phrases, and a check that the verifier hasn't simply pasted the claim text back as their "explanation"). Full detail on this validation is in Chapter 4.5 (Security Issues).

Once the explanation passes client-side validation, `ClaimsContext.tsx`'s verification-submission handler appends the new `Verification` object to the claim's embedded `verifications[]` array and increments `verificationCount` by exactly 1 — a write shape that is independently re-validated by `firestore.rules` (Case C of the `claims/{claimId}` update rule, §4.2.2), so a malicious client cannot forge a verification the server will accept. **The moment `verifications.length` reaches 3, `ClaimsContext.tsx` calls directly into Module 5** (`calculateConfidenceScore()` from `src/lib/confidenceScore.ts`) to compute the final verdict and confidence score in the same write, flipping `status` from `pending` to `verified`. Below the 3-verification quorum, the claim simply accumulates verifications and stays `pending`.

## Module 5 — Weighted Consensus & Confidence Engine

**Core file:** `src/lib/confidenceScore.ts`, invoked from `src/contexts/ClaimsContext.tsx`.

`calculateConfidenceScore()` is a pure function that takes the claim's array of verifications (each carrying `verdict`, `verifierReputation`, and a numeric `sourceQuality` in 0–100) and returns the majority verdict's `agreementRatio`, the `avgReputation` across participating verifiers, the `sourceQualityScore` average, and the final weighted `score`:

$ C = (A times 0.40) + (R times 0.30) + (S times 0.30) $

where $A$ is the percentage of verifiers who agreed with the majority verdict, $R$ is the mean reputation (0–100) of the participating verifiers (pulled live from each verifier's `users/{uid}.reputation` at vote time via Module 1), and $S$ is the mean numeric source-quality score, derived from `determineSourceQuality()`'s domain-whitelist classification (`high` → 100, `medium` → 70, `low` → 30, via `sourceQualityToScore()`). The full worked algorithm is detailed in §4.3.3.

Module 5 also owns **consensus expiry**: `ClaimsContext.tsx` maintains a 7-day `consensusDeadline` (`CONSENSUS_DEADLINE_DAYS = 7`, set at claim creation) and, on a periodic sweep, finds any `pending` claim whose `verificationCount < 3` and whose deadline has passed, computes whatever partial confidence score the existing verifications allow, and force-settles the claim's verdict to `CONTESTED` — this is the only path that produces a `CONTESTED` verdict, and it exists specifically so a claim can never sit in the queue indefinitely for lack of a third verifier. This write path is separately validated in `firestore.rules` (Case B of the `claims/{claimId}` update rule).

Once a claim's `status` flips to `verified` (by quorum or by expiry), Module 5 triggers Module 8 (`NotificationsContext.tsx`) to notify the original submitter, and the claim becomes eligible for Module 6's card generation.

## Module 6 — Fact-Check Card Generator

**Core files:** `src/components/FactCheckCard.tsx`, `src/pages/ClaimDetail.tsx`.

Once a claim carries a final `verdict` and `confidenceScore`, `ClaimDetail.tsx` renders a styled DOM card (`FactCheckCard.tsx`) showing the claim snippet, a color-coded verdict stamp, the confidence percentage, and the cited source(s). `html-to-image` rasterizes this DOM node client-side into a 1080px-wide PNG — the card is laid out at a 540px CSS width and captured at `pixelRatio: 2`, so its height is not fixed but grows with the length of the claim text and the number of cited sources — via the browser's native SVG `<foreignObject>` rendering path — chosen specifically because an earlier hand-written canvas-based parser could not interpret the `oklch()`/`oklab()` CSS color functions used throughout the Tailwind v4 design tokens (see Chapter 2, §2.8), which produced broken/black exports. The user downloads the PNG and forwards it back into the WhatsApp chat the original claim came from, closing the misinformation loop in the same medium it started in. This module is a pure consumer of Module 5's output; it does not write back to Firestore.

## Module 7 — Misinformation Analytics Dashboard

**Core files:** `src/pages/Dashboard.tsx`, `src/components/DashboardChart.tsx`, `src/lib/weeklyReport.ts`.

The Dashboard is intentionally a **public route** (no authentication required — see §4.4) so that the platform's transparency value is not gated behind a login wall. `weeklyReport.ts` computes a rolling 7-day window over the `claims` collection: category distribution (Health/Political/Financial/Religious/Other), verdict distribution, and a "most-debunked" trending list. `DashboardChart.tsx` renders these as Recharts bar/pie visualizations with custom tooltip components (the design system explicitly bans Recharts' default chart chrome). This module reads exclusively from claims that Module 5 has already finalized (or from the live `pending` count for queue-size metrics); it performs no writes.

## Module 8 — System Security & Notifications

**Core files:** `src/lib/security.ts`, `src/contexts/NotificationsContext.tsx`, `src/components/NotificationBell.tsx`, `firestore.rules`.

Module 8 is the cross-cutting layer every other module calls into rather than a step in the linear pipeline. `security.ts` supplies: `sanitizeTextInput()` (XSS defense-in-depth on top of React's JSX auto-escaping, used by Modules 2 and 4), `validateVerdictExplanation()` (used by Module 4), `validateImageUpload()` (triple-layer extension + MIME + magic-byte + size validation, used by Module 2), the idle-session timeout pair `recordActivity()`/`isSessionExpired()` (30 minutes, used globally), and the login rate-limiter `checkLoginRateLimit()`/`recordFailedLogin()`/`resetLoginAttempts()` (5 attempts / 15-minute lockout, used by Module 1's sign-in flow and by `AdminRoute.tsx`'s admin gate). `NotificationsContext.tsx` and `NotificationBell.tsx` provide real-time in-app alerts (`claim_verified`, `reputation_update`, `weekly_report`, `verdict_submitted`) that Module 5 fires into when a claim resolves. Finally, `firestore.rules` is the server-side backstop for every client-side check in this module — the full breakdown of which write paths it governs is in §4.2.2 and §4.5.
