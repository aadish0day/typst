FactStamp's security architecture follows a **defense-in-depth** model: every client-side hardening measure exists for immediate UX feedback and to raise the cost of casual abuse, but none of them is treated as the actual trust boundary — that boundary is always the server-side `firestore.rules` evaluation, which runs independently of, and cannot be bypassed by, any client-side code path. `src/lib/security.ts` is explicitly documented in-code as addressing OWASP Top 10-style vectors (access control, authentication, session hijacking, XSS, file upload, and more); this section covers each mechanism relevant to Chapter 4's system-design scope.

## Dual-Layer Admin Authentication

The `/admin` console (§4.4) is protected by two independent layers that must both pass:

1. **Client-side session flag.** `AdminRoute.tsx` stores `fs_admin_session_unlocked` in `sessionStorage` once a successful admin login completes, purely so the console doesn't re-prompt for credentials on every navigation within the same tab session.
2. **Live Firestore role re-check, on every render.** Regardless of the session flag, `AdminRoute.tsx` computes `hasVerifiedAdminRole = user?.isAdmin === true` from the live, Firestore-backed `useAuth()` snapshot on *every* render. If the session flag is present but the current user's profile does not carry `isAdmin === true`, the flag is discarded (`sessionStorage.removeItem(ADMIN_SESSION_KEY)`) and the user is bounced back to the login gate.

This second layer exists for one specific, explicitly documented reason (verbatim in the source comment): to defeat a DevTools bypass attempt of the form `sessionStorage.setItem('fs_admin_session_unlocked', 'true')`. Setting the flag alone grants nothing, because the render-time check re-derives admin status from the actual Firestore profile every time, not from the flag. And because `isAdmin` on a `users/{uid}` document can only be changed by an existing admin — `firestore.rules`' `isAdmin()` helper and the `users` collection's self-update rule (`isUnchanged('isAdmin')`) jointly guarantee this — there is no client-reachable path to self-promote. The admin gate additionally routes every login attempt through the same rate-limiter described below.

## Login Rate-Limiting

`checkLoginRateLimit()`, `recordFailedLogin()`, and `resetLoginAttempts()` in `src/lib/security.ts` implement brute-force protection, used by both the standard `/signin` flow and the `/admin` login gate — `SignIn.tsx` passes the entered email so the counters are keyed per-identifier, while `AdminRoute.tsx` calls them without an identifier and therefore shares the client-wide `global` counter:

- **`MAX_LOGIN_ATTEMPTS = 5`** — after 5 failed attempts against a given identifier (email/username, normalized and sanitized via `sanitizeIdentifierKey()`), the account is locked out.
- **`LOCKOUT_DURATION_MS = 15 * 60 * 1000`** — a **15-minute** lockout window once the attempt cap is hit.
- Attempt counters are tracked per-identifier (`fs_login_attempts_<key>`) and mirrored into a global client-wide counter; if global failed attempts reach `MAX_LOGIN_ATTEMPTS * 2` (10), a separate global lockout is also triggered — this limits a single client from rapidly cycling through many different usernames to route around the per-identifier limit.
- Counters are persisted in both `localStorage` and `sessionStorage` (`getStorageItem`/`setStorageItem` fall back gracefully if either is unavailable), and a successful login calls `resetLoginAttempts()` to clear both the per-identifier and global counters.
- `formatLockoutRemaining()` renders the remaining lockout time as `MM:SS` for display in the login form's error message (e.g. "Too many failed attempts. Console locked for security. Try again in 14:32.").

This is explicitly a **client-side, per-browser** rate limit (it does not call any server-side throttling API) — it raises the friction cost of a naive brute-force script running in the same browser context, but a determined attacker scripting direct calls to the Firebase Auth REST API from outside the browser is not stopped by this layer alone; the real backstop against credential-stuffing at scale is Firebase Authentication's own server-side abuse protection.

## Idle Session Timeout

`recordActivity()` and `isSessionExpired()` implement a **30-minute** idle-session timeout (`SESSION_TIMEOUT_MS = 30 * 60 * 1000`). `recordActivity()` is called on meaningful user interactions to stamp `fs_last_activity` in `sessionStorage` with the current timestamp; `isSessionExpired()` compares the elapsed time since that timestamp against the threshold. If a session is found idle beyond 30 minutes, the application treats it as expired and requires re-authentication — mitigating the risk of an unattended, still-logged-in browser tab (e.g. on a shared or public computer) being used by someone other than the original user. `clearSecuritySession()` clears both the activity timestamp and the admin session-unlock flag together on logout, so no stale session evidence survives a sign-out.

## Triple-Layer File Upload Validation

`validateImageUpload()` performs four checks, in order, before any screenshot is accepted into the OCR pipeline (Module 2, §4.1):

1. **File size ceiling** — `MAX_UPLOAD_SIZE_BYTES = 5 * 1024 * 1024` (**5 MB**); files above this, or zero-byte files, are rejected immediately.
2. **Extension whitelist** — the filename's extension must be one of `.jpg`, `.jpeg`, `.png`, `.webp`, `.gif` (`ALLOWED_IMAGE_EXTENSIONS`).
3. **MIME type whitelist** — the browser-reported `file.type` must be one of `image/jpeg`, `image/png`, `image/webp`, `image/gif` (`ALLOWED_IMAGE_MIMES`).
4. **Magic-byte signature verification** — the first 12 bytes of the actual file content are read and compared against known binary signatures for each format (`IMAGE_MAGIC_BYTES`: JPEG `FF D8 FF`, PNG `89 50 4E 47`, GIF `47 49 46 38`, WebP's RIFF header `52 49 46 46`). A file must match one of these signatures or it is rejected regardless of what its extension or reported MIME type claimed.

The fourth layer is the one that actually matters against a deliberate attacker: extension and MIME-type checks alone can both be trivially spoofed by renaming a malicious file or forging the `Content-Type` a browser reports, but the magic-byte check inspects the file's real binary header, so a non-image file renamed to `photo.png` (or a polyglot file crafted to pass a MIME check) is still caught. This is described in the source as preventing "MIME spoofing attacks."

## Verdict-Explanation Anti-Spam Validation

`validateVerdictExplanation()` guards the quality of every verification submitted through Module 4's queue (§4.1), applying, in sequence:

- **Minimum length: 50 characters.** Rejects empty or trivially short "explanations."
- **Maximum length: 1500 characters.** Prevents payload bloat and keeps explanations concise (the server-side `firestore.rules` cap on the same field is more permissive, at 3000 characters — the client enforces the stricter UX-facing bound).
- **Minimum word count: 8 words.** Specifically defeats character-padding gibberish like a single repeated string that clears the character-count minimum without containing real content.
- **Repeated-character detection** — a regex (`/(.)\1{5,}/`) flags any single character repeated 6 or more times consecutively (e.g. `"aaaaaa"`, `"......"`, `"!!!!!!"`).
- **Repeated-word detection** — scans the word list for the same word (case-insensitive, punctuation-stripped) appearing three times in a row (e.g. `"fake fake fake ..."`).
- **Generic cop-out / filler phrase blacklist** — a fixed list of low-effort phrases (`"just trust me"`, `"trust me bro"`, `"check it yourself"`, `"search it on google"`, `"search google"`, `"idk"`, `"i don't know"`, `"random text to fill space"`, `"asdfasdf"`, `"qwertyuiop"`) is checked as a substring match against the lowercased explanation.
- **Copy-paste-the-claim detection** — if the explanation text, once lowercased, is identical to (or nearly wholly contains, within a 30-character margin) the original claim text being verified, the submission is rejected — a verifier cannot satisfy the explanation requirement by simply restating the claim back. This check only applies when the claim text is at least 30 characters long.
- **Constructive quality nudge (non-blocking)** — if the explanation contains none of a set of evidence-indicating terms (`source`, `report`, `article`, `study`, `ministry`, `official`, `evidence`, `archive`, `debunk`, `confirmed`, `stated`, `found`, `according`, `data`, `analysis`, `fact`), a soft warning is returned (not a rejection) suggesting the verifier cite specific evidence.

## XSS Input Sanitization

`sanitizeTextInput()` provides defense-in-depth on top of React's own automatic JSX escaping (React already escapes interpolated values by default, so this is a second, independent layer rather than the sole defense). It strips:
- Dangerous HTML tags via `DANGEROUS_HTML_PATTERN` — `<script>`, `<iframe>`, `<object>`, `<embed>`, `<form>`, `<link>`, `<meta>`, `<style>`, `<svg>`, `<math>`, `<base>`, `<applet>` (opening or closing, with any attributes).
- Dangerous event-handler and injection-prone attributes via `DANGEROUS_ATTR_PATTERN` — any `on*` handler attribute (`onclick`, `onerror`, etc.), `srcdoc`, `formaction`, `xlink:href`.
- Dangerous URI schemes via `DANGEROUS_PROTO_PATTERN` — `javascript:`, `vbscript:`, `data:`.
- Null bytes, which are a known technique for bypassing naive string-based filters.

This is applied to user-supplied text fields (claim text, verification explanations) before they are used in contexts where the extra layer meaningfully reduces risk, complementing rather than replacing React's escaping and the server-side length/content constraints in `firestore.rules`.

## The Client Cannot Be Fully Trusted — Server-Side Backing

Every mechanism above is client-side JavaScript, which means every one of them can, in principle, be bypassed by a user who opens their browser's developer console and calls the underlying Firebase SDK directly, skipping the React application entirely. FactStamp's design explicitly accounts for this: **`firestore.rules` re-implements the constraints that actually protect data integrity, independently of the client**, as detailed in §4.2.2:

- The 50–3000 character bound on a verification's `explanation` field (server) backs up the stricter 50–1500 UX-facing bound (client) — even if a client bypassed `validateVerdictExplanation()` entirely, the Firestore rule still rejects an explanation outside its own bounds.
- The `sourceUrl` format check (`^https?://.+`, ≤ 500 characters) is re-validated server-side on the same write path.
- The append-exactly-one-verification-per-write arithmetic (`verificationCount == resource.data.verificationCount + 1`), the `verifierId == request.auth.uid` ownership check, and the live `verifierReputation` cross-check against the caller's actual `users/{uid}.reputation` document are all enforced only by `firestore.rules` — there is no equivalent client-side code, because these are structural integrity guarantees that must hold regardless of which client (or no client at all) issued the write.
- The `imageUrl` format and 800 KB size cap (§4.2.2) is enforced identically whether the image was compressed client-side as intended or a raw, uncompressed payload was pushed directly via the SDK.
- The `isAdmin()` gate (§4.2.2, §4.4) is what actually prevents privilege escalation — the client-side `AdminRoute.tsx` re-check is a UX convenience that happens to align with the same underlying rule, not an independent security boundary.

The general principle applied throughout is: **client-side validation exists to give immediate feedback and to filter out unintentional or low-effort abuse before a network round-trip; server-side Firestore Security Rules exist to make the constraint actually true, because the server is the only party in this architecture that cannot be tampered with by the party trying to bypass a rule.**
