# 3.5 Preliminary Product Description

*(Draft status: content-complete. High-level, module-by-module narrative — one paragraph per module, deliberately kept at a coarser level of detail than Chapter 4's System Design, which will cover schema, procedural logic, and algorithm pseudocode for each of these same modules. Module boundaries and source files follow `Rules/Module-rules.md` exactly.)*

---

FactStamp's functionality is organized into 8 core modules, each responsible for one stage of a claim's lifecycle from initial submission through to a shareable verified verdict, plus a cross-cutting security layer. This section previews each module at a preliminary, product-level description; the detailed data design, procedural logic, and algorithms for each appear in Chapter 4.

**Module 1 — Auth & Verifier Reputation.** This module handles user identity for the entire platform. A visitor registers or signs in using either email/password or Google OAuth through Firebase Authentication (`src/contexts/AuthContext.tsx`, `src/pages/SignIn.tsx`, `src/pages/SignUp.tsx`), and every account is issued a persistent reputation score starting at 50 on a 0–100 scale, stored on that user's Firestore `users/{uid}` profile document. This reputation is not cosmetic — it feeds directly into the weighted-consensus calculation of Module 5, so a verifier's track record of agreeing or disagreeing with eventual consensus has a compounding effect on how much their future votes are trusted.

**Module 2 — Forward Submission (Multimodal Ingestion & OCR).** This is the entry point for every claim into the system. A user can paste raw forwarded text directly, or upload a screenshot of the WhatsApp message as received (`src/pages/Submit.tsx`). Uploaded screenshots are compressed client-side (`src/lib/imageCompression.ts`) and passed through a 100%-client-side Tesseract.js OCR pipeline (`src/services/ocrService.ts`) that extracts the embedded text and strips WhatsApp-specific chat chrome — timestamps, delivery checkmarks, carrier and battery status-bar text — before the claim is normalized and stored, with the module also auto-suggesting a category (health, political, religious, financial, or other) via keyword heuristics tuned for common Indian WhatsApp-forward phrasing.

**Module 3 — Duplicate Detection Engine.** Before a submitted claim is allowed to occupy a new slot in the verification queue, this module checks whether it has effectively already been fact-checked. It computes a Jaccard word-overlap similarity score (`src/lib/duplicateDetection.ts`) between the incoming claim's significant tokens (words longer than 3 characters) and every existing claim's token set. If the highest similarity found is at or above the tuned 0.75 threshold, the submitter is redirected straight to the existing, already-verified claim rather than the community being asked to re-verify a rewording of the same rumour.

**Module 4 — Verification Queue.** Claims that pass the duplicate check as genuinely new enter a public verification queue (`src/pages/VerifyQueue.tsx`), where any authenticated user other than the original submitter can open a claim's verifier workbench (`src/pages/VerifyDetail.tsx`) and submit an evaluation: a verdict, a supporting source URL, and a written rationale — with the source-quality tier derived automatically from the cited domain rather than self-assessed. `ClaimsContext.tsx` enforces that a given user can verify a given claim only once, and that submitters cannot verify their own submissions, keeping the queue's evaluations independent.

**Module 5 — Weighted Consensus & Confidence Engine.** Once a claim has accumulated at least three independent verifications (the quorum threshold, `verificationCount >= 3`), this module computes the claim's final settled verdict and a numeric confidence score using the formula `Confidence = 0.40 × AgreementRatio + 0.30 × AvgVerifierReputation + 0.30 × SourceQualityScore` (`src/lib/confidenceScore.ts`). Source quality itself is derived from a hardcoded domain-credibility list (high-authority government/health domains, medium-tier established news outlets, and everything else scored low). Claims still short of quorum when the `CONSENSUS_DEADLINE_DAYS = 7`-day window closes are automatically settled — their status moves from `pending` to `verified` with the verdict `CONTESTED` — rather than remaining perpetually pending.

**Module 6 — Fact-Check Card Generator.** Once a verdict is settled, this module turns it into a shareable artifact: a PNG image 1080 px wide (a 540 CSS-pixel card captured at 2× pixel ratio), its height growing with the length of the claim text and the number of cited sources, styled to match WhatsApp's native forwarding format and rendered from the on-screen verdict view via `html-to-image` (`src/components/FactCheckCard.tsx`, `src/pages/ClaimDetail.tsx`). This library was specifically chosen (Chapter 2 §2.8) because it correctly rasterizes the OKLCH/OKLAB CSS colors used throughout the app's design system, which an earlier hand-written canvas-based approach could not parse. The exported card can be downloaded and forwarded directly back into the WhatsApp groups where the original misinformation circulated.

**Module 7 — Misinformation Analytics Dashboard.** This module provides a public view into platform-wide trends: category distribution of submitted claims, a rolling weekly report of the most-contested or most-viral claims, verdict-outcome proportions, and a leaderboard of top verifiers by reputation (`src/pages/Dashboard.tsx`, `src/components/DashboardChart.tsx`, `src/lib/weeklyReport.ts`), rendered using Recharts.

**Module 8 — System Security & Notifications.** A cross-cutting module underpinning every other module: client-side input sanitization against XSS, triple-layer upload validation (extension, MIME type, and magic-byte signature check, capped at 5MB), a 30-minute idle-session timeout, and a 5-attempt/15-minute login rate limiter (`src/lib/security.ts`), all backed by matching server-side enforcement in `firestore.rules` so that no client-side rule can be bypassed by a direct, malicious Firestore write. This module also drives real-time in-app notifications (`src/contexts/NotificationsContext.tsx`, `src/components/NotificationBell.tsx`) — for example alerting a submitter the moment their claim reaches consensus.

**Admin Console (cross-cutting moderation layer).** Layered over Modules 1, 4, and 5 (and its own security concerns under Module 8) is the staff-only, unlisted `/admin` console (`src/pages/Admin.tsx`, `Rules/Admin-rules.md`), providing five operational tabs — System Overview, Verifier Directory, Claims Moderation, Incident Queue, and Audit & Tools — with dual-layer authorization (a live-checked client-side `isAdmin` re-verification plus server-side `firestore.rules` enforcement) and an immutable audit trail of every administrative action taken.
