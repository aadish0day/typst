## 3.2.1 Introduction

### 3.2.1.1 Purpose

This section specifies the software requirements for **FactStamp**, a community-powered WhatsApp misinformation fact-checking web application, Version 1.0. It covers the complete client-facing application (submission, verification, consensus, card export, dashboard) and the staff-only `/admin` moderation console, as implemented in the FactStamp codebase (`/home/aadish/Documents/Github/FactStamp`).

### 3.2.1.2 Document Conventions

- **Requirement tags:** Functional requirements are tagged `FR-<MODULE>-<n>` (e.g. `FR-AUTH-1`), grouped by the 8 core system modules defined in `Rules/Module-rules.md`. Non-functional requirements are tagged `NFR-<DOMAIN>-<n>` (e.g. `NFR-PERF-1`).
- **Priority:** Each requirement is rated High (H), Medium (M), or Low (L).
- Requirements are written to be concise, unambiguous, and independently verifiable, per IEEE Std 830-1998 §4.3.

### 3.2.1.3 Intended Audience and Reading Suggestions

- **Project guides and examiners** should read §3.2.2 (Overall Description) for system context, then skim §3.2.3 (System Features) for functional coverage.
- **Developers (the student author, for self-reference during implementation)** should treat §3.2.3 and §3.2.4 as the binding specification against which `src/` was and is checked.
- **Testers** (Chapter 5, Test Case Design) should use the requirement tags in §3.2.3 and §3.2.4 directly as traceability identifiers for test cases.

### 3.2.1.4 Product Scope

FactStamp lets any user submit a WhatsApp forward (text or screenshot) for community fact-checking. The system automatically detects duplicate claims, routes unique claims into a 3-verifier quorum queue, computes a weighted consensus verdict, and lets the result be exported as a shareable PNG card. A staff-only admin console provides moderation and audit tooling. The full functional and quality scope is detailed in §3.2.3 and §3.2.4 below; the narrative problem context is given in §3.1.

## 3.2.2 Overall Description

### 3.2.2.1 Product Perspective

FactStamp is a new, self-contained, client-heavy Single Page Application (React 18 + Vite 5 + TypeScript 5.5 + Tailwind CSS v4) backed entirely by Firebase v12 (Authentication and Cloud Firestore) as a Backend-as-a-Service — there is no custom application server. It is not a follow-on of an existing product; it is a from-scratch capstone project.

### 3.2.2.2 Product Functions

At a high level, the product lets a user:
- Submit a claim as text or a WhatsApp screenshot (with client-side OCR text extraction).
- Have the claim automatically checked for near-duplicates against the existing corpus.
- See unique claims enter a public verification queue.
- Cast a verdict, source URL, and written rationale as a signed-in verifier.
- View a computed weighted-consensus verdict once quorum (≥3 verifications) is reached.
- Export a shareable PNG fact-check card 1080 px wide, with content-dependent height.
- View misinformation trend analytics.
- (Admin only) Moderate users, claims, and incident reports via the unlisted `/admin` console.

### 3.2.2.3 User Classes and Characteristics

- **Registered Verifier** (the platform's single non-staff user class): any authenticated user. Can submit claims, browse the verification queue, and cast verdicts on claims other than their own. No separate "verifier-only" signup path exists — every signed-in user has identical submission and verification privileges, differentiated only by their accrued reputation score.
- **Admin**: a user whose Firestore profile carries `isAdmin: true`. Gains access to the unlisted `/admin` console (5 tabs — see `Rules/Admin-rules.md`) for moderation, override, and audit functions, in addition to all Registered Verifier capabilities.

### 3.2.2.4 Operating Environment

- **Client:** any modern desktop or mobile browser with WebAssembly and ES2022 support (Chrome, Firefox, Safari, Edge — current major versions, see §3.4).
- **Backend:** Google Cloud Firestore (NoSQL, multi-region) and Firebase Authentication. Uploaded screenshots are compressed and persisted as base64 data URIs on the claim document itself, so Cloud Storage is not used at runtime.
- **Hosting:** Firebase Hosting, Vercel, or a self-hosted Docker + Nginx container — all three are supported build/deploy targets.

### 3.2.2.5 Design and Implementation Constraints

- Must operate entirely within the Firebase Spark (free-tier) usage limits — no paid backend infrastructure.
- OCR must run 100% client-side (WebAssembly); no user image may be transmitted to a third-party cloud vision API.
- Card rasterization must correctly render Tailwind v4's OKLCH/OKLAB CSS colors (ruled out a legacy canvas-based parser — see Chapter 2 §2.8).
- All database writes are additionally constrained server-side by `firestore.rules`, so client-side business logic (e.g. quorum counting, reputation deltas) cannot be bypassed by a malicious direct Firestore write.

### 3.2.2.6 User Documentation

A role-based user manual (screen-by-screen walkthroughs for submission, verification, and the admin console) is delivered as part of Chapter 6 (Results and Discussion, §6.2 User Documentation) of this dissertation.

### 3.2.2.7 Assumptions and Dependencies

- Assumes the end user has an active internet connection at time of submission/verification (no offline claim submission).
- Assumes Firebase's free-tier quota (50,000 reads / 20,000 writes per day) is sufficient for the project's academic-demonstration and campus-pilot scale.
- Depends on the continued availability and API stability of Firebase v12, Tesseract.js 7.0, and `html-to-image` as third-party packages.

## 3.2.3 External Interface Requirements

### 3.2.3.1 User Interfaces

The application is a responsive web UI (mobile, tablet, desktop breakpoints) covering: Home, Submit, Verify Queue, Verify Detail (verifier workbench), Claim Detail (verdict + card export), Dashboard, Profile, Sign In / Sign Up, and the unlisted `/admin` console. Standard UI conventions apply throughout (consistent verdict color-coding, category badges, loading skeletons, toast notifications for async actions).

### 3.2.3.2 Hardware Interfaces

FactStamp has no direct hardware interface beyond standard client input devices (touchscreen, keyboard, camera/file picker for screenshot upload). It has no interface to specialized external hardware.

### 3.2.3.3 Software Interfaces

| Interface | Provider | Purpose |
|---|---|---|
| Firebase Authentication | Google Firebase v12 | Email/password and Google OAuth sign-in |
| Cloud Firestore | Google Firebase v12 | Real-time document store for `users`, `claims`, `notifications`, `reports`, `audit_logs`. A `claims/{claimId}/verdicts` subcollection is declared in `firebase.ts` and governed by `firestore.rules`, but is unused at runtime — verifications live as an embedded array on the claim document |
| Firebase Storage | Google Firebase v12 | Rules and emulator port are configured (`storage.rules`), but the client never calls the Storage SDK — screenshots are stored as base64 data URIs on the claim document |
| Tesseract.js 7.0 | Open-source (WASM) | Client-side OCR text extraction |
| html-to-image | Open-source | DOM-to-PNG rasterization for the fact-check card |
| Recharts | Open-source | Dashboard chart rendering |

### 3.2.3.4 Communications Interfaces

All client-backend communication uses HTTPS via the Firebase JS SDK (Firestore's `onSnapshot` real-time listener protocol over WebSocket/long-polling, and standard HTTPS REST for Auth). No custom communication protocol is defined.

## 3.2.4 System Features (Functional Requirements)

Requirements are grouped by the 8 core system modules (`Rules/Module-rules.md`), plus the cross-cutting admin console layer.

### Module 1 — Auth & Verifier Reputation

**Description:** Firebase Auth session management and a persistent 0–100 verifier reputation score stored on each user's Firestore profile. Priority: High.

| ID | Requirement | Priority |
|---|---|---|
| FR-AUTH-1 | The system shall allow a user to register and sign in using email/password credentials via Firebase Authentication. | H |
| FR-AUTH-2 | The system shall allow a user to sign in using Google OAuth. | H |
| FR-AUTH-3 | The system shall assign every newly registered user a base reputation score of 50. | H |
| FR-AUTH-4 | The system shall increase a verifier's reputation by 2 points when their submitted verdict matches the eventual majority (consensus) verdict on a claim. | H |
| FR-AUTH-5 | The system shall decrease a verifier's reputation by 1 point when their submitted verdict disagrees with the eventual majority verdict. | H |
| FR-AUTH-6 | The system shall terminate an authenticated session after 30 minutes of user inactivity (idle timeout). | M |
| FR-AUTH-7 | The system shall lock out further login attempts for 15 minutes after 5 consecutive failed login attempts for the same account. | H |

### Module 2 — Forward Submission (Ingestion & OCR)

**Description:** Accepts a claim as raw text or a WhatsApp screenshot; screenshots are OCR-processed and compressed client-side. Priority: High.

| ID | Requirement | Priority |
|---|---|---|
| FR-INGEST-1 | The system shall allow a user to submit a claim as free-form text. | H |
| FR-INGEST-2 | The system shall allow a user to submit a claim as an uploaded screenshot image (JPEG, PNG, WebP, or GIF). | H |
| FR-INGEST-3 | The system shall extract text from an uploaded screenshot using client-side Tesseract.js OCR, with no image data transmitted to an external OCR service. | H |
| FR-INGEST-4 | The system shall strip WhatsApp chat chrome (timestamps, delivery checkmarks, carrier/battery status bar text) from OCR-extracted text via `cleanExtractedOcrText()` before it is stored or checked for duplicates. | M |
| FR-INGEST-5 | The system shall compress an uploaded image client-side before it is persisted, to keep the stored payload within Firestore's document-size limits. | M |
| FR-INGEST-6 | The system shall auto-classify a submitted claim into one of five categories (health, political, religious, financial, other) using keyword-based heuristics, with the user able to override the suggested category before submission. | M |

### Module 3 — Duplicate Detection Engine

**Description:** Jaccard token-overlap similarity check against the existing claim corpus. Priority: High.

| ID | Requirement | Priority |
|---|---|---|
| FR-DUP-1 | The system shall compute Jaccard similarity `J(A,B) = |A∩B| / |A∪B|` between an incoming claim's token set and each existing claim's token set, using only tokens longer than 3 characters. | H |
| FR-DUP-2 | The system shall redirect the submitter to the existing claim's verdict page when the maximum computed similarity against any existing claim is ≥ 0.75, instead of creating a new claim record. | H |
| FR-DUP-3 | The system shall create a new claim record and enter it into the verification queue when no existing claim matches at or above the 0.75 similarity threshold. | H |

### Module 4 — Verification Queue

**Description:** Lists claims awaiting community verification and provides the verifier workbench. Priority: High.

| ID | Requirement | Priority |
|---|---|---|
| FR-QUEUE-1 | The system shall display all claims with `status = pending` in a public verification queue, visible to any authenticated user. | H |
| FR-QUEUE-2 | The system shall prevent a user from submitting more than one verification on the same claim. | H |
| FR-QUEUE-3 | The system shall prevent a claim's original submitter from verifying their own claim (anti-self-verification). | H |
| FR-QUEUE-4 | The system shall require a verifier to supply a verdict (`TRUE`/`FALSE`/`MISLEADING`/`UNVERIFIABLE`), a source URL, and a written explanation before a verification is accepted; the verification's source-quality tier is derived automatically from the cited domain via `determineSourceQuality()` and is not entered by the verifier. | H |
| FR-QUEUE-5 | The system shall reject a verification explanation shorter than 50 characters or fewer than 8 words, or one that fails the anti-spam / copy-paste-the-claim check in `validateVerdictExplanation()`. | M |
| FR-QUEUE-6 | The system shall surface admin-flagged claims (`adminFlagged = true`) at the top of the verification queue for expedited review. | L |

### Module 5 — Weighted Consensus & Confidence Engine

**Description:** Computes the final verdict and confidence score once quorum is reached. Priority: High.

| ID | Requirement | Priority |
|---|---|---|
| FR-CONSENSUS-1 | The system shall compute a final consensus verdict only once a claim has received at least 3 independent verifications (`verificationCount >= 3`). | H |
| FR-CONSENSUS-2 | The system shall compute the claim's confidence score as `Confidence = 0.40 × AgreementRatio + 0.30 × AvgVerifierReputation + 0.30 × SourceQualityScore`. | H |
| FR-CONSENSUS-3 | The system shall determine `AgreementRatio` as the percentage of participating verifiers whose verdict matches the majority verdict. | H |
| FR-CONSENSUS-4 | The system shall determine source quality from the cited domain against a hardcoded list (High: who.int, pib.gov.in, rbi.org.in, and similar authoritative domains; Medium: bbc.com, reuters.com, snopes.com, and similar; Low: any other domain). | H |
| FR-CONSENSUS-5 | The system shall automatically mark a claim `CONTESTED` if it has not reached a settled majority verdict within `CONSENSUS_DEADLINE_DAYS = 7` days of submission. | H |

### Module 6 — Fact-Check Card Generator

**Description:** Renders a shareable PNG verdict card 1080 px wide, with content-dependent height. Priority: Medium.

| ID | Requirement | Priority |
|---|---|---|
| FR-CARD-1 | The system shall render a fact-check card containing the claim text (or snippet), the final verdict, the confidence score, and the primary cited source. | M |
| FR-CARD-2 | The system shall export the rendered card as a PNG image 1080 px wide — a 540 CSS-pixel card captured at a pixel ratio of 2, its height determined by the card's content — via `html-to-image`, correctly rendering the application's OKLCH/OKLAB design-token colors. | M |
| FR-CARD-3 | The system shall allow the user to download the generated PNG card directly to their device for re-sharing. | M |

### Module 7 — Misinformation Analytics Dashboard

**Description:** Trend graphs, category distribution, and verifier leaderboards. Priority: Low.

| ID | Requirement | Priority |
|---|---|---|
| FR-DASH-1 | The system shall display a rolling weekly trend of claims submitted, broken down by category (health, political, religious, financial, other). | L |
| FR-DASH-2 | The system shall display a leaderboard of the top verifiers by reputation score. | L |
| FR-DASH-3 | The system shall display the proportion of settled claims debunked as FALSE, together with the average confidence score across all settled claims. | L |

### Module 8 — System Security & Notifications (cross-cutting)

**Description:** Client-side defense-in-depth hardening plus real-time in-app notifications. Priority: High.

| ID | Requirement | Priority |
|---|---|---|
| FR-SEC-1 | The system shall sanitize all free-text user input (claim text, explanations, profile fields) against XSS injection before rendering or storage. | H |
| FR-SEC-2 | The system shall validate every uploaded image against a triple layer of checks — file extension, declared MIME type, and magic-byte signature — and reject any file exceeding 5MB. | H |
| FR-SEC-3 | The system shall enforce all data-integrity and access-control rules identically server-side via `firestore.rules`, so client-side bypass of a business rule (e.g. a fabricated verification count) is rejected at the database layer. | H |
| FR-SEC-4 | The system shall deliver real-time in-app notifications covering the four implemented notification types — `claim_verified` (a claim reached consensus), `reputation_update` (the user's reputation changed), `verdict_submitted` (the user's verdict was recorded), and `weekly_report` (the weekly misinformation digest). | M |

### Admin Console (cross-cutting moderation layer, `/admin`)

**Description:** Staff-only unlisted moderation console. Not a numbered core module — per `Rules/Module-rules.md` the admin console is a cross-cutting layer over Modules 1, 4, 5 and 8. Priority: Medium.

| ID | Requirement | Priority |
|---|---|---|
| FR-ADMIN-1 | The system shall restrict access to `/admin` to users whose Firestore profile has `isAdmin === true`, re-checked from the live Firestore-backed auth snapshot on every render (not solely a client-side session flag). | H |
| FR-ADMIN-2 | The system shall provide 5 console tabs: System Overview, Verifier Directory, Claims Moderation, Incident Queue, and Audit & Tools, exactly as implemented in `src/pages/Admin.tsx`. | M |
| FR-ADMIN-3 | The system shall allow an admin to override a claim's verdict, confidence score, status, text, and category from the Claims Moderation tab. | M |
| FR-ADMIN-4 | The system shall allow an admin to promote or revoke another user's `isAdmin` flag, edit reputation, or delete a user account from the Verifier Directory tab. | M |
| FR-ADMIN-5 | The system shall log every mutating admin action to the immutable, append-only `audit_logs` Firestore collection via `addAuditLogToFirestore()` (`firestore.rules` denies all update and delete on that collection). | H |
| FR-ADMIN-6 | The system shall allow an admin to create, investigate, resolve, or dismiss a `ModerationReport` incident ticket from the Incident Queue tab. | M |

## 3.2.5 Other Nonfunctional Requirements

### 3.2.5.1 Performance Requirements

| ID | Requirement | Priority |
|---|---|---|
| NFR-PERF-1 | The verification queue view shall reflect a newly submitted claim within 2 seconds of submission, via Firestore's real-time `onSnapshot` listener. | M |
| NFR-PERF-2 | Client-side OCR text extraction on a typical WhatsApp screenshot (≤ 2MB) shall complete within 8 seconds on a mid-range mobile device. | M |
| NFR-PERF-3 | PNG card export via `html-to-image` shall complete within 3 seconds for a typical 1080 px-wide card. | L |
| NFR-PERF-4 | Duplicate-detection Jaccard comparison against the existing claim corpus shall complete within 500 ms for corpora up to 5,000 claims (client-side, single-pass linear scan). | L |

### 3.2.5.2 Security Requirements

| ID | Requirement | Priority |
|---|---|---|
| NFR-SEC-1 | All Firebase communication shall occur over HTTPS/TLS; no plaintext credential or claim data shall be transmitted. | H |
| NFR-SEC-2 | Admin-only Firestore write paths (e.g. `isAdmin` flag, audit log entries) shall be rejected server-side for any non-admin `uid`, independent of client-side route guarding. | H |
| NFR-SEC-3 | Login attempts shall be rate-limited (5 attempts → 15-minute lockout) to mitigate credential brute-forcing. | H |
| NFR-SEC-4 | A verdict explanation shall be rejected if it falls outside a 50–1,500 character range or fails minimum-word-count / anti-spam heuristics, to deter low-effort or bot-generated verifications. | M |

### 3.2.5.3 Reliability Requirements

| ID | Requirement | Priority |
|---|---|---|
| NFR-REL-1 | A claim that fails to reach a settled quorum-consensus verdict within 7 days shall automatically transition to `CONTESTED` rather than remaining indefinitely pending. | H |
| NFR-REL-2 | The system shall degrade gracefully if client-side OCR fails (e.g. unsupported image format) by allowing the user to manually type the claim text instead of blocking submission. | M |

### 3.2.5.4 Usability Requirements

| ID | Requirement | Priority |
|---|---|---|
| NFR-USE-1 | The claim-submission form shall not require account registration to *view* existing verified claims (browsing is open; submission and verification require sign-in). | M |
| NFR-USE-2 | Verdict states (TRUE/FALSE/MISLEADING/UNVERIFIABLE/CONTESTED) shall be distinguishable by both color and icon/label, not color alone, for accessibility. | M |
| NFR-USE-3 | The application UI shall be responsive across mobile (≥360px), tablet, and desktop breakpoints without horizontal scrolling or layout breakage. | M |

### 3.2.5.5 Scalability Requirements

| ID | Requirement | Priority |
|---|---|---|
| NFR-SCALE-1 | The system shall operate within Firebase Spark (free-tier) quota limits (50,000 reads / 20,000 writes per day) at expected campus-pilot submission volumes. | M |
| NFR-SCALE-2 | The claim data model shall denormalize verifications as an embedded array on the parent claim document (rather than a separate subcollection) to avoid N+1 read patterns as claim volume grows. | L |
