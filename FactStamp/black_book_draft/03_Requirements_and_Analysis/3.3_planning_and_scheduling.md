## 3.3.1 Development Process Model: Agile / Scrum

FactStamp was developed using an **Agile Scrum** process, in preference to a sequential Waterfall or V-Model approach (compared formally in `template/SDLC_Software_Process_Models.md`), because the product's core algorithmic parameters — the Jaccard duplicate-detection threshold, the 40/30/30 consensus weighting, and the OCR text-cleanup heuristics — could only be meaningfully tuned after building a working prototype and observing real WhatsApp-forward text samples. A Waterfall model's up-front, fully-specified design phase would have locked in these parameters before any empirical evidence existed to justify them.

Scrum's three formal roles were held as follows, given the project's single-developer academic context:
- **Product Owner** — the student developer, representing the interests of the end-user (WhatsApp fact-checking community) and the academic requirements of the guides.
- **Scrum Master** — the student developer, self-facilitating sprint cadence and backlog refinement.
- **Developers** — the student developer (solo development), consulting the project guides (Mr. Wilson Rao, Ms. Bertilla Fernandes) at sprint-boundary reviews in place of a formal Sprint Review stakeholder audience.

The project followed Scrum's core artifacts and events at reduced scale appropriate to a single-developer capstone project:
- **Product Backlog** — the full feature list derived from the 8 core modules (§3.5), continuously reordered by priority.
- **Sprint Backlog** — the subset of backlog items selected per 2-week sprint.
- **Increment** — a working, demoable addition to the deployed application at the end of every sprint (never a broken or partial feature left uncommitted).
- **Sprint Planning / Sprint Review / Sprint Retrospective** — held informally at each sprint boundary, with the guide consultation substituting for a full stakeholder review.

## 3.3.2 Sprint Cadence and Incremental Module Delivery

Development proceeded in fixed **2-week sprints**, with each sprint incrementally delivering one or more of the 8 core modules identified in `Rules/Module-rules.md`, rather than attempting to build the entire system before any part of it was testable.

## 3.3.4 Sprint Velocity and Definition of Done

Each sprint's Increment was held to a consistent **Definition of Done**: the feature must be integrated into the deployed application (not left on a feature branch), must not regress any previously delivered module, must pass a manual smoke-test across the primary user flow it affects, and must not introduce a TypeScript compile error (the project's `tsc -b` type-checking gate runs before every Vite production build, and again in GitHub Actions CI).

## 3.3.5 Risk and Contingency Notes

- **Algorithmic tuning risk** (Sprints 3 and 5): the Jaccard threshold (0.75) and the 40/30/30 consensus weighting were not fixed at project start; they were empirically tuned against sample WhatsApp-forward text collected during Sprints 3–5, which is precisely why an Agile/Scrum model was chosen over Waterfall for this project.
- **Third-party dependency risk**: a mid-project migration from a hand-written canvas card-rasterization parser to `html-to-image` (Chapter 2 §2.8) was absorbed within Sprint 6 without disrupting the overall schedule, because Scrum's incremental delivery meant the card generator was not yet a load-bearing dependency for earlier-delivered modules.
- **Solo-developer capacity risk**: because there is only one developer, sprint scope was deliberately kept to one or two modules per sprint rather than attempting parallel workstreams, keeping each 2-week increment realistically achievable.
