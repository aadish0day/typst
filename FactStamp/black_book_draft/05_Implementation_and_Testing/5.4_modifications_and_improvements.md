# 5.4 Modifications and Improvements

Implementation was not a single linear pass — several capabilities were revised after initial delivery, either to fix a real defect discovered during manual testing (§5.3) or to improve on an earlier, weaker implementation. The modifications below are grounded in the project's own `CHANGELOG.md` (`/home/aadish/Documents/Github/FactStamp/CHANGELOG.md`) and the architectural notes in `INDEX.md`, not invented for this report.

## 1. Verification Queue Auto-Replenishment Fix (Bug Fix)

**Problem discovered:** During manual testing, the Verification Queue at `/verify` was found to intermittently display zero pending claims. Root-cause investigation traced this to `applyLocalExpiry()` in `ClaimsContext.tsx` — the automatic 7-day consensus-expiry logic (claims that fail to reach the 3-verifier quorum within their `consensusDeadline` are settled as `CONTESTED`) was correctly resolving overdue claims, but nothing was replenishing the queue with new pending work, so a batch of seeded demo claims could all expire at once and leave the queue empty for anyone evaluating the live application.

**Fix implemented:**
- `scripts/seed-db.mjs` was updated to generate claims with **dynamic future deadlines** (3 to 6 days ahead of the script's execution time) rather than fixed, eventually-stale dates baked in at seed time.
- `applyLocalExpiry()` in `ClaimsContext.tsx` was modified so that whenever expiry processing leaves the database with zero `pending` claims, it automatically replenishes the in-memory claims list with fresh active seed claims (assigning each a new future `consensusDeadline`) — guaranteeing the Verification Queue is never left empty for a verifier to work through.
- The realtime Firestore subscription cleanup in `subscribeClaimsRealtime()` (`firebaseService.ts`) was also hardened to safely tear down both the primary ordered query listener and its unindexed fallback query, preventing a duplicate-listener leak that could otherwise mask the same symptom.

This was manually re-verified by letting seeded claims run past their deadline in the emulator and confirming the queue view (`VerifyQueue.tsx`) always continued to show at least one actionable claim afterward.

## 2. Authentication Security Hardening & Rate Limiting

**Improvement made:** The original sign-in flow had no protection against repeated failed login attempts. `src/lib/security.ts` was extended with a multi-tiered rate limiter:
- Failed attempts are tracked **both per-account** (keyed by a sanitized identifier derived from the email) **and globally per browser client**, using `localStorage` with a `sessionStorage` fallback so a tab reload or browser close cannot be used to reset the counter.
- A **5-attempt threshold** triggers a strict **15-minute lockout** (`LOCKOUT_DURATION_MS = 15 * 60 * 1000`), with `formatLockoutRemaining()` driving a live ticking countdown in the sign-in UI.
- `resetLoginAttempts()` clears the counter immediately on a successful login, so a legitimate user who mistypes a password once or twice is not penalized once they authenticate correctly.
- `SignIn.tsx` was updated to check the rate-limit state *before* dispatching a network request to Firebase Auth (avoiding wasted round-trips against a known-locked account), display an "X/5 attempts left" indicator before lockout, and standardize all invalid-credential error copy to a generic "Invalid email or password" message — closing a user-enumeration side-channel that would otherwise let an attacker distinguish "wrong password" from "no such account."
- The same rate-limiting primitives were also wired into `AdminRoute.tsx`'s login gate, so the staff-only `/admin` console is protected by the identical brute-force defense as the public sign-in page.

## 3. Universal Sliding Dual-Icon Theme Toggle Rollout

**Improvement made:** Plain, inconsistent icon-only theme buttons scattered across different pages were replaced with a single, reusable `<ThemeToggle />` component — a compact pill container with an animated sliding thumb between `Sun` and `Moon` Lucide icons (`translate-x-8`, `duration-300`), fully keyboard-accessible (`role="button"`, `tabIndex`, `aria-label`, Enter/Space key handling). `ThemeContext.tsx` was expanded to expose an explicit `setTheme` alongside the existing `toggleTheme`, so the toggle can be driven both as a simple switch and as a segmented control. The component was then placed consistently across every surface of the application that previously lacked it or used a bespoke variant: the desktop Navbar and mobile navigation drawer, the Admin Command Center's header and Tools tab, the Admin authentication gate (so administrators are not stuck on a jarring theme while unlocking the console), the Sign In / Sign Up auth panels, and the global footer. This closed a real UX inconsistency rather than a functional bug — different pages of the same application previously behaved differently when a user tried to switch themes.

## 4. Pan-Indic Typography Migration (Font-Stack Rework)

**Problem addressed:** The original typography setup loaded three separate Google Font families (`DM Sans`, `JetBrains Mono`, `Lora`) totaling over 120 KB across twelve font files, and — more substantively — had no support for Devanagari script, so Hindi or Marathi text embedded in a WhatsApp forward would render with broken baselines. The Victorian-serif `Lora` styling applied to quoted forward text also had the unintended effect of lending misinformation an unearned air of literary authority.

**Fix implemented:** `DM Sans` was replaced with a single variable Latin font, **Plus Jakarta Sans** (weights 400–800 in one variable file), and **Noto Sans Devanagari** (400/500/600/700) was added specifically for native Hindi/Marathi forward rendering. The monospace `JetBrains Mono` used for numeric figures (reputation ratios, case IDs, countdown timers) was dropped entirely in favor of native CSS `font-variant-numeric: tabular-nums` and `font-feature-settings` on the primary sans font — achieving the same fixed-width alignment for figures like `0/3` or `5d 23h left` at **zero additional network payload**. `Lora` styling was removed from quoted forward text in favor of plain, unadorned message typography. This change touched `index.html`, `src/index.css`, `src/pages/Submit.tsx`, `DESIGN.md`, and `README.md`.

## 5. `html-to-image` Adoption Replacing a Legacy Canvas Parser

**Problem addressed:** The original fact-check card exporter used a hand-written JavaScript canvas-based CSS parser to rasterize `FactCheckCard.tsx` into a downloadable PNG. Once the design system's colors were expressed in Tailwind v4's native OKLCH/OKLAB color space, this legacy parser — which only understood `rgb()`/`hex` syntax — could not interpret the card's actual computed styles, and card exports came out visually broken or entirely black.

**Fix implemented:** The exporter was rewritten around the `html-to-image` library, which rasterizes DOM nodes through the browser's own native SVG `<foreignObject>` rendering path rather than a custom CSS interpreter. Because this uses the browser's real CSS engine, it resolves `oklch()`/`oklab()` (and any other CSS Color Level 4 syntax) exactly as the page itself renders it, eliminating the entire class of color-parsing bugs at the root rather than patching the legacy parser to special-case OKLCH. This also incidentally improved output fidelity — cards now export at a crisp 1080px width, rasterized from the 540px card at a 2× device pixel ratio, with the height scaling to the card's own content and no layout distortion — as documented in both `INDEX.md` and Chapter 2's technology survey.
